1. 今日なにが欠けているのか、そしてなぜか

ステップ 9 はすでにコードを測っており、それを通過させないゲートで行っている。単一のフォーマッタ、サイズの上限（ファイル当たり三百行、関数当たり四十行）、関数ごとの複雑度、重複コード、デッドコード、宣言され使用されている依存関係、ラチェット付きのカバレッジ、そして実際のユーザーがいるところでのミューテーションテストである。その数値は docs/CODE_QUALITY.md に書かれる。これは解決済みである。

解決していないのは製品のもう半分である。ステップ群のコーパスを検証した。ユーザビリティへの、人物やプロファイルへの、機能的グルーピングへの言及は一つもない。今日のインターフェースは二つのものに支えられている。所有者が十秒だけ見るスクリーンショットと、手動のテストケースである。どちらも良いものであり、どちらも人間的で、高価で、忘れっぽい。システムは品質ゲートを立派に通過しながら、使えないままでいられる。すべてが緑で、それでもその人はどこで請求するのかを見つけられない。

さらに、技術的ではあるがインターフェースに現れる第二層の問題がある。同じ製品を複数のプロファイル（管理、運用、照会、顧客）が使うとき、機能は三つの異なる場所——データベース、メニュー、ルートのガード——で有効化され、それらは別々の時点で書かれ、ひとりでに同期を失う。症状はいつも同じである。誰かが自分に属さないボタンを見る。あるいはもっと悪いことに、権限を持っている人がその画面を見つけられない。

続く二つのヒューリスティクスは、同じ形態でその二つの問題に取り組む。検証可能な言明の短いカタログ、それらを自動で測る少数の計器、そしてプロジェクトが外に出る必要があるときのための、宣言された例外の道である。

2. モデル：三つの層、規則の単一の形態

誘惑は、規則の一覧を作り、それを最初のプロジェクトのスタックに縛り付けることである。それは悪く老化する。React の規則は Angular には適用されず、Angular の規則はテンプレート付きサーバには適用されず、二年後には一覧の半分が死んでいる。提案は三つの層を分ける。

第 1 層 — 非依存の中核（交渉不能）。 道具についての言明ではなく、結果についての言明である。「フォーマッタは一つしかなく、誰もそれと議論しない」は、TypeScript でも PHP でも Go でも同じように適用される。中核は安定した識別子で列挙され、プロジェクトごとに変わらない。

第 2 層 — スタックごとのアダプタ（設定可能）。 中核の各規則について、フロントエンドの各ファミリが*何で*測り*どのしきい値で*測るかを宣言する。Vite を使う React のプロジェクト、Next のプロジェクト、Angular のプロジェクト、テンプレート付きサーバのプロジェクト、モバイルのプロジェクト、コマンドラインのプロジェクトは、同じ中核の六つの異なるアダプタである。ここに、ユーザーが「フロントエンドごとに設定可能」として求めたもののすべてが住む。

第 3 層 — プロジェクトの決定（宣言されたもの）。 具体的なしきい値と免除である。発明されるのではなく、所有者に求められて書かれる。アーキテクチャのステップのサイジングと同じである。しきい値が宣言されていなければアダプタのものが走り、そのように記録される。

各規則は常に、六つの欄からなる同じカードで書かれる。

3. 四つの計器

どのヒューリスティクスも、その検証が意見であれば役に立たない。計器は四つであり、各規則はどれに属するかを宣言する。

  1. 自動ゲート。 毎回のプッシュとブロックの閉鎖で走る。緑か赤を返す。安価で、反復可能で、議論しない。数えられるもののすべてを測る。
  2. マトリクスへの問い合わせ。 プロファイルごとの機能マトリクス（B2 を参照）は宣言的な成果物であり、メニュー、ルーティング、権限はそこから導出される。マトリクスを点検することはインターフェースを点検することである。ユーザビリティの一部を機械で検証できるものに変える部品がこれである。
  3. プロファイルごとのエンドツーエンド・テスト。 宣言された各プロファイルについて、そのプロファイルとして入り、到達可能な機能の集合をマトリクスの行と比較するスクリプト。*少なすぎても多すぎてもならない*。典型的な二つの同期ずれ（余分なボタンと欠けた画面）を捕まえるテストである。
  4. 手動のケース。 どの機械も判断しないもの。グルーピングが理解できるか、作業が助けなしに完了するか、テキストがユーザーの言語にあるか。人とともに実行し、ステップ 10 がすでに命じているとおりに記録する。

5. パート B — ユーザビリティ

六つのファミリ。第一と第二は所有者が明示的に求めたものであり、他の三つは、それらがなければグルーピングとプロファイルが同じように、ただより遅く劣化するから存在する。 六番目は後から生まれた。2026-10-27（D-070）で、性質が違う。最初の五つはシステムが人に見せる画面についてであり、六番目はシステムが作られる会話についてである。

B1 — 機能的収束によるグルーピング

母なる規則：機能は、その人がしに来たことによってグループ化され、それが生まれたモジュールによってではない。 コードはエンティティ（「請求書」「顧客」「支払」）で組織される。人はそうではない。誰も「エンティティを管理する」ためにシステムに入らない。入るのは請求するため、出荷するため、月末を締めるためである。メニューがエンティティを見せるなら、その人が翻訳者の役をする。メニュー*が*仕事である。

B3 — 状態、そして何かがないときに人が見るもの

「動かない」という苦情のほとんどは、「何もない」「読み込み中」「失敗した」と言えなかった画面である。四つの状態を、常に、すべての一覧とすべての詳細画面で。

B6 — 所有者への問い

この方法はプロンプトの半分以上で、モデルに尋ねることを命じている。公開された資料の二十七ファイルのうち十五で、二十二回。しかし 2026-10-27 まで、どう尋ねるかはどこにも書かれていなかった。だから形は場任せになり、所有者は問いを裸で受け取った。それを正当化するデータもなく、選択肢もなく、推奨もなく。これは第 11 段が追う非対称そのものである——片側で要求し、もう片側で定義しない——しかも最も高くつく方向、決める人の側で。方法はすでに二度これをやっている。第 8 段は「赤を見せて」で満足せず、受領とは何かを定義した。第 12 段は「報告して」で満足せず、検証済みと信じていることを分けた。

id規則検証重大度
UX-28エージェントが所有者の決定を必要とするとき、問いは四つの部分を伴い、この順で届く。それを必要にしているデータを列挙して。それらをつないで問いが見えるようにする五行以内の段落。取りうる答えに番号を振った問いそのもの。そしてエージェントの推奨。そしてプロジェクトが宣言した技術的な深さで。裸の問いは、なぜそれを尋ねられているのかを再構成する仕事を所有者に残す。ペンディングの閉鎖時の所有者のレビューAVISA

三つの深さの水準と、その出どころ。 プロジェクトが一つを宣言し、エージェントはその水準で話す。beginner（日常の言葉、結果に向けて、ファイル名も専門用語もなし）、decision_maker（測った数字と帰結、ファイルの道筋なし。方法が既定で使うもの）、technical（ファイル、行、コマンド）。この規則のために発明したものではない。初心者の水準はすでに方法全体の形である（D-025）。パラメータの名と三つの値はデータの層、project_config.communication_depth に住む。消費する道具が推測せずに読まなければならないものだからである。

この規則が約束しないこと。 compuerta は、その条項が七十二のプロンプトと八つの言語にあることを検証できる——実際にする。だが、ある火曜日にモデルが書いた具体的な問いが四つの部分を備えているかは、どの試験も検証できない。それを judge するのは所有者であり、だからこの規則は警告しブロックしない。ブロックするのに誰も検証できない規則は、警告する規則より悪い。CQ-12 と CQ-14 がすでに持つ、同じ宣言された限界である。

6. どこに掛かるか、そしてどんな成果物を生むか

本付録は新しいステップを発明しない。存在するものに掛かる。それによってゲートの複製を避け、ユーザビリティの一覧の通常の行き先、すなわち一度読まれて終わることを避ける。

どこに置くか（D-043）。 四つの区間に横断的であり、主な重みは建設ループ（ステップ 5 から 12）にあり、そこが決定され建設される場所である。独自のステップではない。番号付きのステップはラダーの再番号付けを強制し、ステップの数え方を変え、付録を八言語への契約の義務的翻訳に従わせることになり、建設が緑で通る前にそれを要求することになる。しかもループがすでに持たないゲートを一つも加えない。

どう掛かるか（D-044）。 一つの正典の出所、五つのアンカー、二つの事前入口。規則のテキストはここにだけ住み、プロンプトはそれを引用する。決してコピーしない。四十五の規則をループの八つのプロンプトの中で繰り返すと、それらを薄める（各ステップ自身の仕事と競合し、エージェントは毎回違う仕方で従う）。それらを派生させる（同じテキストの二つのコピーはひとりでに同期を失う。ステップ 11 が追うアンチパターンである）。そしてそれらをより横断的にするわけではない。規則を横断的にするのは、各ブロックが同じゲートを通ることなのであり、規則がどこにでも書かれていることではない。

プロンプトに入る唯一の規則と、その理由（D-070）。 UX-28 は上の原則に対する書かれた例外であり、他の四十五とどこが違うかを言っておくべきである。あちらは作られるシステムへの要求で、compuerta はプロジェクトが書き残す成果物の上で測る。UX-28 は作られる会話への要求で、モデルがそれに従う唯一の道は、モデルが読むものの中にあることである。狭く入る——四つの部分とパラメータを名指し、それ以上は言わない——八つの言語で同一の、たった一つの英語の文として。この例外が認めないのは、他のどれかを写すことである。D-044 の論は、compuerta が見られるすべてについて丸ごと立っている。

事前入口 1 — 適用範囲の定義ユーザーの用語集、docs/GLOSSARY.md に用語集がなければ、UX-01 と UX-24 は比較する相手を持たない。
事前入口 2 — 適用範囲の定義プロファイルの一覧、docs/PROFILES.md に一覧がなければ、B2 のマトリクスはステップ 5 で発明され、そこから導出されるすべてが根拠なしに生まれる。
アンカー 1 — ステップ 5（計画）画面に触れるすべてのペンディングは三つのことを宣言する。どの収束グループに属するか（B1）、どのプロファイルがそれを持つか、どの受け入れ基準がプロファイルごとか（「プロファイル X において、人は Y ができ、Z はできない」）。その宣言がなければペンディングはステップを通らない。ここでグルーピングとプロファイルが*生まれる*。それらは計画の決定であり、コードの決定ではない。最も生産性の高いアンカーであり、今日存在しないものである。
アンカー 2 — ステップ 8（赤いテスト）マトリクスは、まず失敗するのが見えるテストになる。プロファイルごとに、到達可能なものをその行と比較する（UX-11、UX-12、UX-15）。これがなければマトリクスは誰も見ない文書である。

アンカー 5 — ステップ 12（検証と正直な報告）報告は何を測ったか、何が avisa に残ったか、どの規則が消されているかを、その理由、認可者、再検討日とともに言う。沈黙の損害ゼロ。消されたグループは充足として読まれてはならない。

各ブロックの閉鎖最初のクリックのテスト（UX-07）、実環境のスクリーンショット（UX-27）、そしてマトリクスの二つのエンドツーエンド・テスト。自動化できない三つの検証である。

状態（D-049）。 五つのアンカーは接続済みである。ステップ 5、8、9、10、12 の冒頭プロンプトが本書を八言語で引用し、英語の一文はすべてで同一、その隣に各国語の翻訳が置かれている。本書は残りのメソッドとともに八言語でサイトに公開され、その二つのプロンプトは契約 anexo-h として docs/html/api/prompts.json に入った。そこから build/prompts.mjs が八言語でバイト比較し、一致しなければビルドは失敗する。

8. 二つの部品、本方法が使う形態で

コード品質。

Set up and maintain the code-quality gate for this project, configured for its frontend family. The core rules are the same in every project; what changes is how each one is measured and at which threshold. Install one formatter and one linter with a single shared configuration; enforce size limits per file and per function, complexity per function, duplication, dead code, declared-and-used dependencies, type checking where the language allows it, coverage with a ratchet, and secret scanning. Where the project has real users, add mutation testing scoped to the changed lines and record the score per block. Then extend the gate to the frontend itself: no business rule inside a screen, one typed client for every server call, one home for shared state, no user-visible string outside the translation catalogue, a stable identifier and role on every interactive element, styling only through tokens, and automatic basic accessibility checks. Every rule has a stable id, a severity (blocks, warns, records) and a named verifier. Thresholds and exceptions are declared by the owner in one configuration file; a rule switched off without a written exception is a gate failure, not a decision. Report the result per rule in docs/CODE_QUALITY.md, not as a single number.

When you need a decision from me, ask it with the four parts of UX-28 (docs/ANEXO_HEURISTICAS.md) and in this order: the data that makes the question necessary, listed; one paragraph of at most five lines that links that data and lets the question be seen; the question itself with its possible answers numbered; and your recommendation. Say it at the technical depth the project declared in communication_depth -- beginner, decision_maker or technical; if the project declared none, use decision_maker.

このプロジェクトのコード品質ゲートを、そのフロントエンドのファミリに合わせて設定し、構築して維持せよ。中核の規則はどのプロジェクトでも同じである。変わるのは、各規則を何で測り、どのしきい値で測るかである。フォーマッタを一つ、リンタを一つ、単一の共通設定でインストールせよ。ファイルごとおよび関数ごとのサイズ上限、関数ごとの複雑度、重複、デッドコード、宣言され使用されている依存関係、言語が許すところでの型検査、ラチェット付きのカバレッジ、シークレットの走査を強制せよ。プロジェクトに実際のユーザーがいるところでは、変更された行に限定したミューテーションテストを加え、スコアをブロックごとに記録せよ。次にゲートをフロントエンド自体へ広げよ。画面の中に業務規則を置かないこと、サーバへのすべての呼び出しに対して一つの型付きクライアント、共有状態のための一つの置き場所、翻訳カタログの外にユーザーに見える文字列がないこと、すべてのインタラクティブな要素に安定した識別子とロール、スタイルはトークンのみを通すこと、そして基本的なアクセシビリティの自動検査である。すべての規則は安定した識別子、重大度（ブロックする、警告する、記録する）、そして名前のある検証器を持つ。しきい値と例外は所有者が一つの設定ファイルで宣言する。書かれた例外なしに切られた規則は、決定ではなくゲートの故障である。結果は単一の数値ではなく、docs/CODE_QUALITY.md に規則ごとに報告せよ。

私の決定が必要になったら、UX-28（docs/ANEXO_HEURISTICAS.md）の四つの部分を、この順で示して聞いてください。その問いを必要にしているデータを箇条書きで、それらをつないで問いが見えるようにする五行以内の段落、取りうる答えに番号を振った問いそのもの、そしてあなたの推奨。プロジェクトが commun ication_depth で宣言した技術的な深さで——beginner、decision_maker、technical——。宣言がなければ decision_maker を使ってください。

ユーザビリティ。

Build the usability criteria for this project before writing the first screen, and enforce them where the method already has hooks. Group functionality by what the person came to do, never by the internal module or the data entity: every menu group is named with a user job in the project glossary, every functionality has exactly one canonical home, no functionality is orphaned, and every group is reachable in no more than three steps from the entry screen. Then declare accessibility in one matrix and derive everything from it: each functionality lists the profiles that have it, each functionality has at least one profile, each profile has at least one functionality and its own entry point, the navigation is generated from the matrix instead of written by hand, and every route checks the permission on the server because hiding an entry is not protecting it. Verify the matrix per profile with an end-to-end check that compares what is reachable with the matrix row: neither less nor more. Require the four states on every list (with data, empty, loading, error), a visible working indicator with the option to cancel long operations, an error message that says what happened and what to do without losing entered data, a primary action per screen, confirmation or undo for destructive actions, and a form that keeps what was typed. Run each manual test case once per affected profile, run the first-click check at the close of every block, and require a real screenshot of the test environment on every item that touches a screen. Record the result per rule, with owner-declared exceptions, in docs/USABILITY.md, and keep the matrix in docs/PROFILE_MATRIX.md as the single source of truth.

When you need a decision from me, ask it with the four parts of UX-28 (docs/ANEXO_HEURISTICAS.md) and in this order: the data that makes the question necessary, listed; one paragraph of at most five lines that links that data and lets the question be seen; the question itself with its possible answers numbered; and your recommendation. Say it at the technical depth the project declared in communication_depth -- beginner, decision_maker or technical; if the project declared none, use decision_maker.

最初の画面を書く前に、このプロジェクトのユーザビリティ基準を組み立て、本方法がすでに掛かり所を持っている場所でそれらを強制せよ。機能はその人がしに来たことによってグループ化し、内部のモジュールによってもデータのエンティティによっても決してグループ化するな。メニューの各グループはプロジェクトの用語集にあるユーザーの仕事で名付け、各機能はちょうど一つの正規の家を持ち、どの機能も孤児にならず、すべてのグループは入口画面から三ステップ以内で到達可能でなければならない。次にアクセシビリティを一つのマトリクスで宣言し、そこからすべてを導出せよ。各機能はそれを持つプロファイルを列挙し、各機能は少なくとも一つのプロファイルを持ち、各プロファイルは少なくとも一つの機能と独自の入口点を持ち、ナビゲーションは手書きではなくマトリクスから生成され、すべてのルートはサーバ側で権限を検証する。入口を隠すことは保護することではないからである。マトリクスをプロファイルごとに、到達可能なものをマトリクスの行と比較するエンドツーエンドの検査で検証せよ。少なすぎても多すぎてもならない。すべての一覧に四つの状態（データあり、空、読み込み中、エラー）を要求せよ。長い操作をキャンセルする選択肢を伴う可視の進行中指示、入力済みのデータを失わずに何が起きたかと何をすべきかを言うエラー・メッセージ、画面ごとに一つの主操作、破壊的な操作に対する確認または取り消し、そして入力されたものを保つフォームを要求せよ。各手動テストケースを影響を受けるプロファイルごとに一度実行し、各ブロックの閉鎖時に最初のクリックのテストを実行し、画面に触れるすべてのペンディングにテスト環境の実際のスクリーンショットを要求せよ。結果を規則ごとに、所有者が宣言した例外とともに docs/USABILITY.md に記録し、マトリクスを唯一の真実の源として docs/PROFILE_MATRIX.md に保て。

私の決定が必要になったら、UX-28（docs/ANEXO_HEURISTICAS.md）の四つの部分を、この順で示して聞いてください。その問いを必要にしているデータを箇条書きで、それらをつないで問いが見えるようにする五行以内の段落、取りうる答えに番号を振った問いそのもの、そしてあなたの推奨。プロジェクトが commun ication_depth で宣言した技術的な深さで——beginner、decision_maker、technical——。宣言がなければ decision_maker を使ってください。

9. この提案がしないこと

12. コンプライアンス・ダッシュボード（決定済み：二つの数値、D-047）

状態。 2026-10-22 に D-047 で決定された。ダッシュボードは二つの数値で行き、レギュレーションの指紋を伴い、ラチェットを伴い、人間のものを割合の外に置き、座席を必須とする。ブロックを閉じる権限は与えない。以下は実装（PND-002）が満たさなければならない仕様である。

何であるか。 ゲートがすでに出した規則ごとの結果からの決定論的な派生物である。新しいものを測らず、新しいものを判断しない。数える。もしダッシュボードが規則の評決を変えられたなら、同じものに対して二つの真実の源があることになり、それはまさに本付録が UX-10（ナビゲーションはマトリクスから導出される）と CQ-14（共有状態の単一の場所）で戦っているものである。

何でないか。 受け入れ基準ではない。どの数値もブロックを閉じる権限を与えない。緑か赤かは、ブロックする各規則が一つずつ決める。ダッシュボードは傾向を記述し、何を見るべきかを指す。閉鎖のしきい値として使われ始めたら、役に立つのをやめる。数値を上げる最短の道は規則を消すことだからである。

二つの数値、決して一つではない。

数値式何を測るかどう動くか
コンプライアンス通る規則 ÷ 有効な規則見ているものがどれだけきれいか直すと上がる
ゲートのカバレッジ有効な規則 ÷ カタログに宣言された規則付録のどれだけが実際に見ているか規則を消すと下がる

二つである理由：規則を消すとコンプライアンスは上がり、カバレッジは下がる。単一の数値では消すことは無料であり、ダッシュボードは盲目を報いる。反対の方向に動く二つの数値では、近道は消える。より良いダッシュボードを見せるには、規則を消すのではなくコードを直さなければならない。そしてカバレッジは測ることなしには上げられない。

レギュレーションの指紋。 各記録は、どの物差しで計算されたかを保存する。カタログの版、有効な規則と消えた規則、フロントエンドのアダプタ、道具の版である。それがなければ、昨日の 82 と今日の 91 は同じように書かれても同じ測定ではない。二つの異なるレギュレーションであり、系列は偽である。指紋のない二つの数値は進歩の幻想を生み、それはダッシュボードを持たないより悪い。指紋が変われば、記録は比較不能と印され、そうでなければ履歴は現行の物差しで再計算される。決してそれを言わずに並べてグラフ化しない。

ラチェット。 コンプライアンスは、それを説明する記録された決定なしにブロックから次へ下がらない。CQ-08 でテストのカバレッジがすでに持っているのと同じ仕組みである。今日の数値が明日の床である。下げることは禁じられていない。記録なしで下げることは禁じられている。

勘定に入らないもの。 人だけが判断できるもの——最初のクリックのテスト（UX-07）、タスクテスト（UX-06）、スクリーンショット（UX-27）、そしてすべての手動のケース——は、ブロックごとに名前と日付とともに合格または不合格として記録され、人間による検証のカバレッジとして別に報告される。コンプライアンスの割合には入らない。混ぜれば、結果は六十パーセントが測定で四十パーセントが意見の数値になり、どれがどちらか誰にも言えない。だから第 9 節はなお有効である。ダッシュボードはユーザビリティの評点を発明せず、規則を数える。

どう反証するか。 第 11 節の受け入れテストを拡張する。

シナリオ要求される結果

どこに現れるか。 ステップ 12 の正直な報告（アンカー 5）に、この順で。まずゲートの二値の評決、次に二つの数値、次に何がいつまで消えているか、次に前のブロックに対する動きと、その名指された原因である。常に座席を伴う。*四ポイント下がった：CQ-15、請求画面のカタログ外の三つの文字列*。座席のない数値はノイズである。座席こそが、コードを読まない所有者にとってそれを実行可能なものにする。
