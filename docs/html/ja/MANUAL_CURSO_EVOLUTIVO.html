始める前に

このパートは誰のためか

第一部をやって、現実には空のフォルダを渡されることなどほとんどないと気づいた人のため。渡されるのは既に動いているシステムで、それに依存するユーザーがいて、「これを直して」か「あれを足して」と言われる。そして数か月前に何かを「バイブコーディング」して、動いて、今は崩れないようにその上に構築を続けなければならない人のためでもある。二人は同じ場所にいる：レガシーとともに。たとえ片方はそれを自分で書いたのだとしても。

最後に何を手にするか

受け継いだのと同じシステムが、以前と同じことをしていて、しかし周りに方法が前提とするすべてを備えている：レガシーのルールを備えた共働の約束。各主張がどこから出たかの印とともに復元されたシステムの地図。コードがすることと業務が信じていることのあいだの食い違いの一覧。速度の印付きでバックログに変わった監査。匿名化されたデータを持つテスト環境。繰り返せるデプロイ。コードの外に出してローテーションした秘密。重要なフローを見張る特性化テスト群。既に世界へ作用しているものの上の錠。計測された数字によるサイジング。そして負債と顧客の依頼がモジュールごとに対になって同居するバックログ。その後に、赤のテストとともに修正された最初のバグと、完全な方法で構築された最初の新しい機能。

ガイドプロジェクト：「受け継いだTurnera」

第一部と同じ診療所の、二年後、別の時間軸だ：彼らはTurneraを方法で作ることが決してなかった。その代わりに、責任者の甥が一夏で「Turnos」というウェブアプリケーションを作り、それ以来動いている。今日、二人の受付係と三人の専門職が毎日使っていて、約二万件の予約が入っていて、それを丸ごと理解している人は誰もいない：甥は外国に住むようになり、二週間に一度メッセージを返す。

あるもの。 コードの入ったGitHubのリポジトリ（ブランチは一つ、コミットのメッセージは「修正」など）、アプリケーションが動くのと同じサーバーの上のデータベース、FTPでファイルをコピーする手でのデプロイ、コードに書かれたデータベースのパスワード、テストはゼロ、毎晩リマインダーを送るサーバーの定期処理、そして責任者がデスクトップのツールでデータベースにつないで毎月落とす表計算。誰も復元したことのない「自動」のバックアップがある。

痛むもの。 二つ。一つ目はバグだ：患者が時々リマインダーを二度受け取り、時々一度も受け取らない。責任者はいつ起きるか分からないが、苦情を言う患者のスクリーンショットを持っている。二つ目は足りないものだ：ある種の予約について支払いリンクで手付金を求めたいし、表計算を落とさずに今月の予約数、欠席数、キャンセル数を見たい。

オーナー。 同じ責任者：事業についての判断力があり、一日十五分、コードは読まない。そして重要な新しい点が一つ：彼女はシステムがしないことをすると信じていて、システムが実際にしていることを知らない。レガシーではそれが普通であり、それこそレッスンN2が明るみに出すものだ。

重要なフロー、彼女の言葉で：「予約を登録する」「予約をキャンセルする」「リマインダーが届く」「患者を探す」「今月の表計算を落とす」。五つあり、それが特性化テスト群になる。

これで足りる。ほかのすべてはシステムの中にあり、それを読むのはエージェントだ。

正常化の区間：レッスンN0からN7

この八つのレッスンが、第一部になかった区間だ。最初の四つは読み取りのためのもの：何も変えないし、何かを変えたい誘惑は巨大になる。次の二つが安全ベルトを組む。最後の二つが測って順序を付ける。機能に触れるのはその後だ。

レッスン N0 — 既存システムの適格性：エージェントが実際に行って検証する前提条件

理解すべきこと。 レッスン0では基準に答えるのは調査だった。ここにはシステムがある。だから基準は、誰の意見も介さずに、エージェントが実際に行って検証できる：ソース、データ、永続化を含む完全な環境を立ち上げられるか。コードを理解できるか。コードだけから、機能のすべてを記述し、責任者が自分のシステムだと認める文書を書けるか。テスト用の道具で画面を操作し、エンドツーエンドのテストを走らせられるか。今日の道具で構築されているか。データを複製し匿名化でき、復元されたバックアップがあるか。連携にテストモードはあるか。七つの前提条件であり、新しいルールは、赤は「不可」ではないということだ：それは前段のプロジェクトであり、独自の範囲を持ち、そのシステムを適格にするためのものだ。

プロンプトを送る前に、あなたの手で：

  • docs/INITIAL_SURVEY.md、短く：責任者によればTurnosは何をして誰のためか、何が痛むか（二重のリマインダー、足りないもの）、誰が作ってどれだけで返事が来るか、どこで動いているか、誰がアクセスを持つか、そして誰も復元したことのない「自動」のバックアップがあること。半ページ。
  • docs/ELIGIBILITY_CRITERIA.md：レッスン0のシートに、レガシーの七つの前提条件を加えたもの（進化・修正の道のページ、ステーションN0から写すこと）。空の三列とともに：緑か赤か、証拠、前段のプロジェクト。
  • リポジトリへの読み取りアクセス、データベースの複製（または読み取り専用の本番）、そしてエージェントがシステムを立ち上げようと試せる場所（コースではあなたのマシンで足りる）。認証情報はチャットの外に。

レッスン N1 — レガシーのための共働の約束

理解すべきこと。 レッスン1の六つのルールに五つが加わる。それが存在するのは、他人のコードを前にしたモデルが反射的に三つのことをするからだ：並べ替える、悪いと思ったところを「直す」、そして自分の期待と違うことをコードがしていたらそれは誤りだと決めてかかる。レガシーのルールはその反射を塞ぐ：頼まれていないリファクタリングはしない、触れる前に読む、変なものは直さずに書き留める、オーナーが別のことを言うまで現在の挙動が仕様である、そして特性化が緑でなければ何も入らない。

  • あなたの働き方の好み、レッスン1と同じく。そしてもう一つの決定：正常化のあいだにどれだけのリスクを受け入れるか。コースでは：エージェントは自分でテスト環境にデプロイしてよい。本番へは、レッスン15まで決して。
  • docs/ELIGIBILITY.md が締め済みであること。

(8) Code you do not understand is read before it is touched, and what you learn goes into the system map. (9) Anything strange you find (a secret in the code, a dead path, a duplicated rule, a query without an index) is logged as a pending item with its evidence, never fixed in passing. (11) No change reaches the test environment without the characterization suite green. Add any rules you think this system needs, marked as proposals. レッスン N2 — システムの読み取り：復元された地図と食い違い

理解すべきこと。 コース全体で時間あたりの価値が最も高いレッスンだ。レッスン2ではプロジェクトファイルとツリーは調査から出てきた。ここではシステムそのものから出てきて、各主張がどこから出たかの印を帯びる：[コード]、[データベース]、[設定]、[文書]、 [業務]、または[推定]。印こそがコードを読まずに検証することを可能にする：推定されたものを見て、確認するか訂正する。そして新しい文書が現れる、食い違いの一覧だ：コードがすること、データベースが課すこと、業務が信じていることのあいだで合わないすべて。それは勝手には解決しない：一つずつがあなたの、日付付きの決定だ。レガシーには常に食い違いがある。一覧が空で出てきたら、エージェントは比較していない。

  • リポジトリの外に住むものの一覧：リマインダーの定期処理と、データベースにつなぐ月次の表計算。
  • docs/WORKING_AGREEMENT.md が締め済みであること。

完全性の検証。 バグを再現するテストの赤を、数字とともに見たか？ 根本原因は修正の前に散文で書かれていたか？ 特性化は緑のままか？ 対のものはそれぞれ自分の証拠とともに閉じたか？コミットは「赤で証明」と言っているか？

提出物。 完全なルーチンで閉じたバグ、閉じた対のもの、そしてバグのテストで拡張された特性化テスト群。

典型的な誤り。 根本原因を読まずに修正を許可すること：Turnosでは、エージェントの最初の仮説はたいてい「処理が二度走っている」で、それは真実の半分だ。そして「ついでだから」とメッセージのモジュールを片付けさせること：ルール7だ。

ガイドプロジェクトでは。 テストは、予定変更された予約で二重の送信を再現する：夜の処理は翌日の予約の行ごとに一通のリマインダーを送り、予定変更された予約には行が二つある（どの画面も表示しない「予定変更済み」の状態の古い行と、新しい行）。一度も受け取らないのは、送信の後に予定変更された人たちだ。根本原因：レッスンN2で現れた「予定変更済み」の状態。業務の質問：「予定変更された予約は新しい予約か、同じ予約か？」。責任者が決める：同じ予約、履歴付きで。根での修正は送信ではなく状態に触れる。対になった冪等性は同じブロックで払われる。赤は「予約1件に対してメッセージ2通」と言い、緑は「予約1件に対してメッセージ1通」と言う。そして挙動の変更が申告される：予定変更された予約が月次の表計算に二度現れなくなる。表計算はテーブルの消費者だからだ。責任者がそれを承認する。

レッスン R2 — 二つ目のブロック：手付金を、進化モードで

理解すべきこと。 古いものの上の新しいものは、第一部のレッスン5から12そのままに、完全な方法で構築する：保留項目の中の仕様、日付付きの決定、赤のテスト、エンドツーエンドの検証、誠実な報告。違いは二つ。近隣の回帰はシステム全体であり、それを言うのは特性化テスト群だ。そしてブロックがあるモジュールに入るとき、そのモジュールの「触れたときに払う」と印された正常化の保留項目が、自分の証拠とともに一緒に入る。レガシーが古いモジュールにしたことを、新しいモジュールにしてはいけない。

プロンプトを送る前に、あなたの手で：

  • docs/PENDING.md の中の手付金の進化の保留項目を、あなたが読んだ完全な仕様、その対のもの、そして責任者が既に取れる業務の決定とともに：どの予約に手付金が付くか、いくらか、払われなかったらどうなるか。
  • 帰結のある行動の調査（N5）に「手付金を請求する」の行を加えたもの。世界へ作用する新しい行動だからです：レッスン14と同じく、構築の前に錠を。
  • 緑の特性化テスト群。
  1. レッスン5の開始のプロンプトで、手付金の依頼についてブロックを開き、責任者として仕様を読むこと。
  2. 構築の前に、錠：「手付金を請求する」の行動について、レッスン14の締めのプロンプトを、まずドライランモードで貼ること。
  3. レッスン8のルーチンで、保留項目ごとに、対のものを同じブロックに入れて構築すること。
  4. ブロックの締めに：完全なエンドツーエンドのテスト群（特性化のものに新しいテストを加えたもの）を、レッスン8のブロックの締めのプロンプトで。そしてあなたがシステムを使うしばらくの時間。

完全性の検証。 手付金には、請求が存在するより前に赤のテスト付きの錠があるか？ ブロックの後も特性化は緑のままか？ モジュールの対のものは払われたか？ 古いモジュールで、保留項目なしに「改善」されたものはないか？

提出物。 テスト環境でドライランモードで動いている手付金、その仕様、その錠、そのテスト、そのエンドツーエンドの検証とともに。そして閉じた対のもの。

典型的な誤り。 収まりがいいからと「残りと同じやり方で、速く」手付金を構築すること：新しいモジュールは常に完全な方法とともに生まれる。そして「支払いリンクであって我々が請求するわけではない」と錠を忘れること：リンクは患者に送られる。それは外へ向かう行動だ。

ガイドプロジェクトでは。 手付金はリマインダーと同じ経路を使い、その経路には今やキューがある（N6の非対称な決定が独りで元を取っている）。錠：受付係の明示的な確認と専門職が定めた金額。しばらくのドライランモードで「手付金を求めたはずの相手」を記録する。キャンセルの画面の対のもの（確認）は、手付金がキャンセル時に起きることを変えるので、このブロックで払われる。締めに、テスト群は七つのフローを走る：特性化の五つ、R1のバグのもの、そして手付金のもの。

その後：本番リリースと運用

ここからは、レガシーは方法を持つシステムであり、第一部のレッスン13から22がそのまま当てはまる。注記が四つ。一つ目は運用品質の六つの段についてだ：最低限の可観測性と脆弱性の走査はもう安全ベルトとともに入っており、永続化の計測はもうN6にあり、負荷テストはその量で最初のデプロイの前に走らせる。二つの監視は最初の読みを基準線として始まり、初日にもう悪かったものはその印とともに保留項目になる。残り三つの注記はこれだ。レッスン13の監査はN3のものと比べる：負債をどれだけ払い、どれだけ残っているか。レッスン20のマニュアルはレガシーには存在しないことが多く、あるがままのシステムと、今や本当にやったことを文書化している閉じた保留項目から生成する。そしてレッスン23の振り返りにはこの道固有の質問がある：正常化にいくらかかったか（時間で、トークンで、最初の変更までの段階数で）、そして「待てる」と印した負債のうち、結局同じだけ高くついたのはどれか。その答えが、次の版でこのパートの順序を修正することになる。

正常化の区間の修了リスト

オーナーがコードを読まずに検証する、最初のブロックを開く前の八つの条件。進化・修正の道のページのものと同じだが、このパートの提出物なのでここで繰り返す。

  1. 前の段階のすべての入力（調査、適格性、約束、プロジェクトファイル、ツリー、環境、ボリューム、サイジング、ゲート）が出所の印付きで存在し、オーナーが推定の各ノードを確認した（N2）。
  2. 各食い違いに日付付きの決定があり、システムを変えるものには保留項目がある（N2）。
  3. 監査が存在し、各発見に速度の印がある（N3）。
  4. 安全ベルトが緑：匿名化されたデータを持つテスト環境、二度走ったデプロイ、外に出してローテーションした秘密、継続的インテグレーション、ミューテーションによる赤を実証した特性化テスト群（N4）。
  5. すべての帰結のある行動に判定があり、「今」の錠に赤のテストがある（N5）。
  6. 一次の数字が計器とテストとともに計測されていて、「十倍」が書かれている（N6）。
  7. 「ブロックする」が一つも開いておらず、顧客の各保留項目に対のものがある（N7）。
  8. 約束にレガシーの五つのルールがあり、新しいセッションが読み取りテストを通る（N1、N2）。
