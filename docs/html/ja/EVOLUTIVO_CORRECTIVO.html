なぜこのページが存在するか

はしごを書いたとき、私は空のフォルダを見ながら書いた：第0段はプロジェクトに取り組むかを決め、第4段は機能のない骨組みをデプロイし、第5段になってようやくユーザーが見る最初のものが現れる。きれいな場合であり、最もよく教える場合でもある。だが最も頻繁な場合ではない。実務では、誰かが私を呼ぶときの大半は、既に動いていて、それに依存するユーザーがいて、もういない誰か、あるいは誰も証拠を求めなかったモデルが作ったシステムがあり、依頼は「これを直して」か「あれを足して」だ。私自身のツールは、はしごが書かれるずっと前から診断モードで他人のシステムに入っていたし Ref. 11、方法が初めて本番のシステムから栄養を得たのは、既に存在していたものを見ているときだった Ref. 12。

そしてここに、先へ進む前に名指ししておきたい罠がある：レガシーを前にした誘惑は、どちらも間違っている二つの極端のどちらかを選ぶことだ。一つは「方法でゼロから書き直す」：きれいに聞こえるし、ほとんど常に、最初のシステムを置き換えるに至らない二番目のシステムで終わる。もう一つは「直接ループを当てる、そのために第5段から第10段があるのだから」：実際的に聞こえるが、砂の上に建てることだ。ループは契約が、地図が、テスト環境が、動くテスト群が、繰り返せるデプロイが存在することを前提にしているからだ。方法で生まれなかったシステムには、そのどれも存在しない。この道は真ん中を行くものだ：まず正常化し、書き直さず、それからはしごを登る。

方法の三つのユースケース

方法には三つのユースケースがあり、エージェントを開く前にどれにいるかを知っておくとよい。どこから入るかが変わるからだ。

ケース出発点どこから入るか入口はどれだけ続くかどこに書かれているか
新規プロジェクト空のフォルダと依頼を持つオーナー。第0段、そこから十六を順に。最初の機能の前に一週間の立ち上げ。主文書、十六の契約、コースのマニュアル。
方法で作られたシステムへの進化・修正システムは既にはしごを登っている：契約、地図、証拠付きで閉じた保留項目、テスト群、デプロイ、マニュアルがある。第5段：ブロックを開いてループを辿る。第11段は定期的に。第15段は段階の締めに。なし：次の段階のために第15段が第0段へ戻るだけで、既に主文書のパートBにある。主文書（フェーズ4、運用）。
方法なしで作られたシステムへの進化・修正動いていて、ユーザーがいて、それらの成果物が一つもないか、いくつかが中途半端なシステム。このページの正常化の区間（N0からN7）、そしてその後にようやくループを、修正モードか進化モードで。小さいシステムで二週間から三週間、機能の最初の一行に触れる前に。このページとコースのマニュアル、パート2。

混同されないよう名指ししておく、外に残るもの：技術の移行（プラットフォームの変更、言語の変更、データベースの変更）は方法のユースケースではない。それは別のプロジェクトであり、一般には第0段の排除基準に当たる Ref. 46。受け継ぐシステムにアクセス可能なリポジトリがないか、その画面をプログラムから操作できず操作可能にもできないなら、相応しいのはそれを正常化することではなく、第0段を丸ごと通した、それを置き換える新規プロジェクトだ。

そして三番目のケースに当てはまる一言：レガシーが他のチームのものか自分のものかは同じことだ。三か月前にモデルと一緒に証拠なしで構築したシステムは、三年前に請負業者が作ったものとまったく同じだけレガシーだ。変わるのは読む労力であって、道ではない。

原則：書き直さずに正常化する、すべての入力とともに

正常化とは、システムを、方法がループを開くときに前提としている状態まで持っていくことだ。そしてそれを、私が譲らない三つのルールで行う。

第一：書き直さない。 正常化は機能に触れない。システムの周りに足りないもの（契約、地図、テスト環境、テスト群、繰り返せるデプロイ、既に世界へ作用しているものの上の錠）を置き、システムは以前と同じことをしたままにする。レガシーは、直すべきだったバグよりも「全部片付けよう」という熱意によって壊れることの方が多い。

第二：二つの速度。 負債には、どんな変更よりも前に払う部分があり、それを安全ベルトと呼ぶ：実データに似たデータを持つテスト環境でシステムを走らせられること、繰り返せる形でデプロイできること、秘密をコードの外に置くこと、そしてそのどれかが変わったら赤になる、重要なフローの特性化テスト群を持つこと。安全ベルトは硬いゲートだ：それなしには何も変えない。例外は、本番の緊急のために書かれた一つだけで、後ほど説明する。残りの負債は 触れたときに払う：ブロックがあるモジュールに入るとき、そのモジュールの正常化の保留項目が一緒に入る。決して「全体清掃の一週間」ではない。

第三：前の段階のすべての入力が存在しなければならない。たとえ自動発見で復元する必要があっても。 これがこの道を「ループを当てるだけ」から区別するルールだ。立ち上げ区間の各段は後続の段が読む成果物を生む：初期調査、適格性シート、共働の約束、プロジェクトファイル、セマンティックツリー、ボリュームの調査、サイジング、環境の調査、ゲート。新規プロジェクトではそれらの入力を、オーナーがエージェントとともに取り込みから書く。レガシーでは誰も書いておらず、ループはそれなしには始められない。解決は飛ばすことではない：エージェントが システムそのものから復元することだ。コードを、データベースのスキーマを、各環境の設定を、ログを、あるだけの文書を読み、それらの文書の各主張がどこから出たかの印を帯びるようにする。私が使う印は五つ：[コード]、[データベース]、[設定]、[文書]、[推定]、加えてオーナーが確認または訂正したものには[業務]。印の付いた復元された文書は、コードを読まずに検証できる文書だ：オーナーは[推定]と印された主張を見て確認するか訂正し、[コード]と印されたものを見てシステムが自分の思っている通りのことをしているか確かめる。合わないものは 食い違いであり、食い違いは正常化の金塊だ：誰も報告しなかったバグであり、誰も決めなかったルールだ。

正常化の区間：八つのステーション

はしごの十六と混同されないよう、これらを段ではなくステーションと呼び、N0からN7と番号を振る。新しい段ではない：立ち上げの段と運用の三つ（第8段、第11段、第12段）を、別の順序と別の入口で並べたものだ。新規プロジェクトでは入口が調査であり、ここでは入口がシステムで、読むのはエージェントだ。

ステーション由来する段新規プロジェクトとの違い
N0 — 既存システムの適格性0基準が四つ多い。X2は画面ごとに測る。赤なら、それは条件ではなく最初の保留項目だ。
N1 — レガシーのための共働の約束1ルールが五つ多い：頼まれていないリファクタリングをしない、触れる前に読む、ついでに直さず書き留める、現在の挙動が仕様である、特性化が緑でなければ何も入らない。
N2 — システムの読み取り2調査、プロジェクトファイル、ツリーが、出所の印付きでコードから出てくる。食い違いの一覧が現れる。
N3 — 棚卸しとしての監査11最後ではなく最初に行き、各発見がブロックするか、触れたときに払うか、待てるかを言う。
N4 — 安全ベルト4、7、13データ付きのテスト環境、繰り返せるデプロイ、外に出した秘密、継続的インテグレーション、そして特性化テスト群。硬いゲート。
N5 — コードからの錠と地図12、8何も変える前に、世界へ作用するすべてと、部分と部分のあいだのすべての契約を棚卸しする。
N6 — 実数でサイジングする3、9一次の数字は聞くのではなく測る。オーナーはデータベースにないものだけを提供する。
N7 — 正常化のバックログ5負債と顧客の依頼を一つのキューに、速度の印とモジュールごとの対付きで。

順序が重要だ。N3がN4より前なのは、監査が安全ベルトに何が入るべきかを言うからだ（見つけた秘密、操作できない画面、繰り返せないデプロイ）。N5が安全ベルトの後なのは、帰結のある行動を棚卸しするには、間違えても高くつかない場所でシステムを走らせられる必要があるからだ。N6が最後なのは、N4でようやく存在するデータ付きのテスト環境の上で測るからだ。そしてN7が締めるのは、それ以前のすべてを一つのキューにまとめるからだ。

いつ：正常化のカレンダー

週ステーションほかに何が起きるか
1N0、N1、N2、N3オーナーを隣に置いてシステムを読む。ノードを確認し、食い違いを決める。何も変えない。週の締めに：復元された地図と負債の棚卸し。
2N4、N5安全ベルト：データ付きのテスト環境、二度繰り返したデプロイ、ローテーションした秘密、重要なフローの特性化テスト群。既に作用しているものの上の錠を確認。締めに：システムがテスト環境で動き、テスト群が緑。
3N6、N7、そして最初のブロック計測したサイジング。順序の付いたバックログ。第5段で最初のブロックを開く。修正か進化か、正常化の保留項目を対にして。ここから先はいつものループだ。

システムが大きければ、伸びるのは週1（読むものが多い）と週2の特性化テスト群（フローが多い）だ。N7は伸びない：書くのに一週間かかる正常化のバックログは、誰も維持しないバックログだ。

N0 — 既存システムの適格性

  • 意図：このシステムを方法で引き受けられるかを、触れる前に決める。二つの排除基準は第0段と同じで、X1（アクセス可能で標準的に管理されたリポジトリ）とX2（プログラムから操作でき、バックエンドへの効果を検証できる画面）だが、ここではX2を既にあるものの上で画面ごとに測り、赤なら始めるための条件ではない：バックログの最初の保留項目であり、ブロックすると印される。
  • いつ：一度だけ、最初の日。二時間。
  • 入力：初期調査（依頼、誰がシステムを使うか、何が痛むか）、リポジトリへの読み取りアクセス、できれば動いている環境へのアクセス。
  • 成果物：決定を記した docs/ELIGIBILITY.md、そしてレガシーのために加える四つの基準：どう動くか知っている人がいるか（そしてどれだけ時間があるか）、本番を読み取り専用で参照できるか、自動テストが存在するか、バックアップが存在し一度でも復元されたことがあるか。
  • ゲート：X1が緑。X2が緑か、そのブロックする保留項目が開いている。バックアップがN4の前に少なくとも一度復元されている。
  • 誰が決めるか：オーナー。

プロンプトを送る前に、これが存在しなければならず、作るのはあなた（またはあなたと業務）であってエージェントではありません：

  • docs/INITIAL_SURVEY.md、初日に書ける短い版：業務によればシステムは何をして誰のためか、今日何が痛むか（依頼のきっかけとなったバグ、足りないもの）、誰が作ったか、その人はつかまるか、どこで動いているか、誰が何にアクセスできるか、バックアップはあるか誰が取るか。半ページ、意図的に不完全に：N2でエージェントがシステムから完成させます。
  • docs/ELIGIBILITY_CRITERIA.md：第0段のシート（X1、X2と重み付けのもの）に、レガシーの基準のための四行を加えたもの：知っている人、参照できる本番、既存のテスト、復元されたバックアップ。答え、出所、緑か赤かの列は空のままで。
  • エージェントのためのリポジトリへの読み取りアクセス、可能ならテスト環境か読み取り専用の本番へのアクセスも、認証情報はチャットの外に。
  • 受け入れられる最低限の状態：エージェントがリポジトリをクローンでき、あなたは誰がシステムを作ったかとそれが生きているか（システムも人も）を知っています。

最初の：

We are going to assess whether this existing system can be taken over with the Urazuke method. Read the initial survey in docs/INITIAL_SURVEY.md and the criteria sheet in docs/ELIGIBILITY_CRITERIA.md, which for an existing system adds four criteria: whether anyone who knows how the system works is available; whether production can be queried read-only; whether any automated test exists; and whether a backup exists and has ever been restored. Then explore the repository and, if I gave you access, the environment where it runs: change nothing. Fill in the sheet criterion by criterion with the answer, its source (survey, code, database, configuration, or inferred) and, for the exclusionary criteria X1 and X2, green or red. For X2, list every screen and say for each whether it can be driven by a program today and whether the effect can be checked in the backend. If a criterion cannot be answered from what you have, ask me; do not assume. Do not decide: present me the completed sheet with your reading and your doubts, and I will decide. Reply in my language.

この既存システムをUrazukeの方法で引き受けられるかを評価します。docs/INITIAL_SURVEY.md の初期調査と docs/ELIGIBILITY_CRITERIA.md の基準シートを読んでください。シートは既存システムのために四つの基準を加えています：システムがどう動くか知っている人がつかまるか。本番を読み取り専用で参照できるか。自動テストが存在するか。そしてバックアップが存在し、一度でも復元されたことがあるか。その後リポジトリを、そしてアクセスを与えたなら動いている環境を探索してください：何も変えないでください。シートを基準ごとに、答え、その出所（調査、コード、データベース、設定、または推定）とともに埋め、排除基準X1とX2については緑か赤かを書いてください。X2については、各画面を列挙し、それぞれについて今日プログラムから操作できるか、効果をバックエンドで確認できるかを言ってください。手元のもので答えられない基準があれば、私に聞いてください。推測しないでください。決定はしないでください：完成したシートをあなたの読みと疑問とともに私に提示してください。私が決めます。私の言語で答えてください。

求めているのは、第0段と同じことに三つの違いを加えたものだ。何も変えずにシステムを探索すること。ここには探索すべきシステムがあるからだ。各答えがどこから出たかを言うこと。調査が短く、答えの大半はコードから来るからだ。そしてX2を画面ごとに測ること。レガシーでは答えがシステム全体について「はい」や「いいえ」になることは決してなく、「この四つははい、この二つはいいえ」であり、その二つが最初の保留項目だからだ。

プロンプトを送る前に（締めのプロンプト）：完全なシートを読んだ後に下した、一行のあなたの決定。検証可能で三つを超えない条件（N4の前にバックアップを復元するという条件はほとんど常にその一つです）。そしてX2が赤の画面の一覧。プロンプトがそれを最初の保留項目に変えます。

N7 — 顧客の依頼と対にした正常化のバックログ

  • 意図：完全な仕様を持つ保留項目の一つのキュー。そこに負債（監査から出たもの、食い違い、操作できない画面、未実装の錠、サイジングの決定）と顧客の依頼（修正すべきことと追加すべきこと）が同居し、それぞれが速度の印を持ち、モジュールごとに対になっている。二つの列を加えた第5段だ。
  • いつ：三週目、区間の締めに。半日。その後はループ。
  • 入力：docs/AUDIT_[fecha].md、決定を書き込んだ docs/DISCREPANCIES.md、 docs/LOCKS.md、docs/SIZING.md、セマンティックツリー、そしてこの段階に対する顧客の依頼。
  • 成果物：すべての保留項目が仕様付きで、「ブロックする／触れたときに払う／待てる」と「修正／進化／正常化」の印付きで、モジュールごとの対とともに書かれた docs/PENDING.md。
  • ゲート：最初のブロックの前に「ブロックする」と印された保留項目が一つも開いていない。顧客の各保留項目に、一緒に入る正常化の保留項目が列挙されている。
  • 誰が決めるか：オーナーが、順序について。

プロンプトを送る前に、これが存在しなければならず、作るのはあなた（またはあなたと業務）であってエージェントではありません：

  • この段階に対する顧客の依頼を、散文で、顧客の言葉で、二つの一覧に分けて：今日失敗していること（それぞれ、業務によればどう再現するか、何が起きるか、何が起きるべきか）と、 足りないこと（新しいもの）。docs/blocks/STAGE_01_REQUEST.md でも好きな場所でも構いません。プロンプトは「the client's request for this stage」と言うので、どこにあるか伝えてください。オーナーが優先順位を出したなら、それも。
  • N2からN6までのすべての成果物が締め済みであること：ツリー、監査、決定済みの食い違い、錠、サイジング。どれかが欠けているならこのプロンプトを開かないでください：バックログが不完全に出てきて、何が足りないのか分からなくなります。
  • 既に存在するブロックする保留項目（N0、N3、N4のもの）が閉じているか、日付付きで進行中であること。
  • 受け入れられる最低限の状態：顧客の依頼がその言葉で二つの一覧になっていて、前のステーションの成果物が存在します。

最初の：

正常化とこの段階に対する顧客の依頼を、docs/PENDING.md の中の番号付き保留項目の一つのキューに変えます。それぞれ方法が求める完全な仕様付きで（番号、題名、セマンティックツリーのノード、出所、記述、決定と日付を伴う業務ルールまたは欠落と印したもの、入るデータと出るデータ、画面、境界ケース、「ある状況を前提に、あることが起きたとき、ならば」の形の受け入れ基準、どう検証するか、状態）。正常化の項目の出所：docs/AUDIT_[fecha].md、変えると私が決めた食い違い、プログラムから操作できない画面、ローテーションすべき秘密、まだ実装されていない錠、そして docs/SIZING.md の決定。それぞれが速度の印を保ちます：ブロックする、触れたときに払う、または待てる。顧客の項目の出所：この段階に対する顧客の依頼。それぞれに修正（今日失敗していること、顧客の言葉による再現の仕方とともに）または進化（新しいこと）と印してください。顧客の各項目について、同じモジュールに触れていて一緒に払うべき正常化の項目を列挙してください。依頼がどこかの点で曖昧で検証可能な項目を書けないなら、私に聞いてください。推測で解決しないでください。順序：ブロックする項目を先に、その後に顧客の項目を私が与えた優先順位で、それぞれ対になった正常化とともに。私の言語で答えてください。

求めているのは、完全な第5段（詳細な仕様は各保留項目の中に住む。正常化のものにも）に、この道を成り立たせる二つの印を加えたものだ。速度は各負債をいつ払うかを言い、種類はどう閉じるかを言う（修正は失敗を再現するテストで閉じ、進化は第7段のテストで閉じる）。そしてモジュールごとの対、これは「触れたときに払う」のルールを運用可能にしたものだ：「手付金」のブロックを開くとき、支払いモジュールの正常化の保留項目が一緒に入り、それより前でも後でもない。

締めの： 第5段の各セッションのルーチンを、変更なしで、共働の約束の中に。

完全性の検証：「ブロックする」が開いたまま残っているか？ ならば最初のブロックは開かない。各修正は顧客の言葉で再現の仕方を言っているか？ 顧客の各保留項目には、たとえ空でも対の一覧があるか？ 警告サイン：バックログに「待てる」の正常化の保留項目が五十を超えている。それは記録された負債ではない：一覧に変装した書き直しだ。決して払われないものは保管庫へ送って、そう言うこと。

受け継いだシステムの上のループ：修正モードと進化モード

N7を終えると、道ははしごと合流する：第5段から第10段を保留項目ごとに登る。新規プロジェクトと同じく、同じ契約と同じプロンプトで。だが一節を割く価値のある二つの機微がある。それは「方法でレガシーに触れる」を「注意深くレガシーに触れる」から区別するものだからだ。

修正モード：赤は自然なもの

修正の保留項目はバグだ：今日失敗していて、顧客がそれを知っている。新規プロジェクトの第7段では赤は作り出される（テストを書き、古いコードに対して走らせ、失敗するのを見る）。修正では赤はバグそのものだ：失敗を再現するテストを、報告したユーザーのように画面からフローを操作して書き、それが現在のコードに対して失敗しなければならない。失敗しないなら、報告されたバグを再現していない。別のものを再現したのだ。その赤は正しいものを直していることの証明であり、「起きているに違いないこと」についてのエージェントのどんな説明よりも価値がある。根本原因まで四ラウンドかかった事例 Ref. 22 が、書かれた再現なしには各ラウンドが別々の症状を直すのだと私に教えた。

プロンプトを送る前に、これを手元に持っていなければなりません：

  • docs/PENDING.md（N7）の中の修正の保留項目。顧客の言葉による再現の仕方付きで：何をして、何が起きて、何を期待していたか。顧客が再現の仕方を知らないなら、まず事例（レコード、日付、スクリーンショット）を手に入れること。再現なしにテストはなく、テストなしに締めはありません。
  • テスト環境で緑の特性化テスト群（N4）、コマンドは docs/STATUS.md に。
  • これと対になった正常化の保留項目、その保留項目の中に列挙されていること。
  • 決める覚悟：根本原因が、誰も書かなかった業務ルールだったとき（よく起きます）、エージェントは止まって聞いてきます。誰かがその日のうちに答えなければなりません。
  • 受け入れられる最低限の状態：テスト環境で手でバグを再現できます。

修正の保留項目を閉じるための：

This pending item is a correction: [what fails, in the client's words, and how to reproduce it]. Before changing anything: (1) Reproduce the failure with a test that drives the flow from the screen and checks the effect in the backend, and show me that it fails against the current code; that red is the proof that you reproduced the right defect. If you cannot reproduce it, tell me what you tried and what you need; do not fix what you cannot see. (2) Find the root cause and tell me in prose, with the evidence, before fixing. If the root cause is a business rule nobody wrote down, stop and ask me. (3) Fix at the root, not where it hurts, and nothing else: anything else you find goes to a pending item. (4) Show me the test green, the characterization suite still green, and the regression of the neighbouring items. (5) If the fix changes a current behaviour that someone may depend on, say so explicitly: that is a decision for me, not a side effect. Close the paired normalization items of this module in the same block, each with its own evidence. The commit message says "proved red against [version]" and the test counts. Reply in my language.

この保留項目は修正です：[何が失敗するか、顧客の言葉で、そしてどう再現するか]。何かを変える前に：(1) 画面からフローを操作してバックエンドでの効果を確認するテストで失敗を再現し、現在のコードに対して失敗することを私に見せてください。その赤が、正しい欠陥を再現したことの証明です。再現できないなら、何を試して何が必要かを私に言ってください。見えないものを直さないでください。(2) 根本原因を見つけ、直す前に、証拠とともに散文で私に言ってください。根本原因が誰も書かなかった業務ルールなら、止まって私に聞いてください。(3) 痛むところではなく根で直し、それ以外は何も：ほかに見つけたものは保留項目へ行きます。(4) テストが緑であること、特性化テスト群がまだ緑であること、そして近隣の項目の回帰を私に見せてください。(5) 修正が、誰かが依存しているかもしれない現在の挙動を変えるなら、はっきりそう言ってください：それは副作用ではなく私の決定です。このモジュールの対になった正常化の保留項目を同じブロックで、それぞれ自分の証拠とともに閉じてください。コミットのメッセージには「[バージョン]に対して赤で証明」とテストの数を書いてください。私の言語で答えてください。

求めているのは、診断の前の再現だ。モデルは再現していないものをとても自信ありげに診断するからだ。触れる前の散文による根本原因、あなたが的外れな修正を止められるように。根とそれだけ、レガシーでは「ついでだから」が動いていたものを壊す最も多い形だからだ。システム全体の回帰としての緑の特性化。そして条項5、挙動の変更を決定に変えるもの。そして対：このモジュールの負債は「後で」ではなく今、その証拠とともに払われる。

進化モード：特性化が回帰である

進化の保留項目は、存在するものの上の新しい何かだ。第5段のプロンプトで開き、第6段と第7段でそのまま構築し、唯一の違いは「近隣の回帰」が何を意味するかだ：ここでは近隣はシステム全体であり、動いていたものが動き続けていると言うのは特性化テスト群だ。ルールがもう二つ。第一：ブロックがあるモジュールに入るとき、そのモジュールの「触れたときに払う」と印された正常化の保留項目が、自分の証拠とともに一緒に入る。二つの速度のルールだ。第二：新しいものは最初から完全な方法とともに生まれる。つまり、保留項目の中の仕様、赤のテスト、エンドツーエンドの検証、そして世界へ作用するなら錠とともに。レガシーが古いモジュールにしたことを、新しいモジュールにしてはいけない。

例外：本番の緊急

安全ベルトは硬いゲートであり、硬いゲートには書かれた例外が必要だ。書かなければ、夜の十一時に何かが落ちた日に例外が発明されるからだ。例外はこれだ：本番が落ちているかデータを損なっていて、安全ベルトがまだ完成していないなら、損害を止める最小限を、手での戻り道付きで、オーナーに知らせた上で行う。そして同じ日のうちに修正の保留項目を開き、完全なルーチンで閉じる：それを再現する赤のテスト、根本原因、回帰。ループへ戻ってこない緊急の修正は、利息付きで取り立てられる負債だ。

プロンプトを送る前に、これを手元に持っていなければなりません：本当に緊急であることの確認（本番が落ちているかデータを損なっている。「顧客がピリピリしている」ではありません）、知らせたオーナー、そして戻る方法（N0のバックアップか前のバージョン）が手元にあること。

緊急のための：

This is an urgent fix on production: [what is happening]. Do the minimum that stops the damage, on a branch, with the rollback ready before you deploy, and tell me exactly what you changed and what you did not verify. Do not touch anything else. Then, today, open the corrective pending item in docs/PENDING.md with what happened, and we close it with the full routine: the test that reproduces it in red, the root cause, the fix at the root, the characterization suite and the regression green. Reply in my language.

これは本番での緊急の修正です：[何が起きているか]。損害を止める最小限を、ブランチの上で、デプロイする前にロールバックを用意した上で行い、正確に何を変えて何を検証しなかったかを私に言ってください。ほかには何にも触れないでください。その後、今日のうちに、docs/PENDING.md に何が起きたかを記した修正の保留項目を開いてください。それを完全なルーチンで閉じます：それを再現する赤のテスト、根本原因、根での修正、特性化テスト群と回帰が緑であること。私の言語で答えてください。

求めているのは、最小限を、戻り道を後ではなく先に用意して、検証していないことの誠実な報告（第10段）とともに。そして同じ日のうちにループへ戻る義務、それが例外を習慣から分けるものだ。

システムが正常化されたと言えるのはいつか

完全にはならないし、それでいい：「触れたときに払う」と印された負債は何か月もかけて、モジュールごとに払われ、「待てる」と印されたものは払われないまま終わることもあり、それは言わなければならない。はっきりした瞬間を持つのは区間の締めで、それは最初のブロックを開くときだ。その一覧がこれだ：

  1. 復元される入力の表のすべての入力が出所の印付きで存在し、オーナーがツリーの[推定]のノードをすべて確認した（N2）。
  2. 各食い違いに日付付きの決定があり、システムを変えるものには保留項目がある（N2）。
  3. 監査が存在し、各発見に速度の印がある（N3）。
  4. 安全ベルトが緑：あなたが開いた、匿名化されたデータを持つテスト環境。二度走ったデプロイ。空の秘密の検索と、見つかったもののローテーション。緑の継続的インテグレーション。各重要なフローについてミューテーションによる赤を実証した、緑の特性化テスト群（N4）。
  5. すべての帰結のある行動に判定があり、「今」と印された錠に赤のテストがある（N5）。
  6. 一次の数字が計器とテストとともに計測されていて、「十倍」が書かれている（N6）。
  7. 「ブロックする」と印された保留項目が一つも開いておらず、顧客の各保留項目に対のものがある（N7）。
  8. 共働の約束にレガシーの五つのルールがあり、新しいセッションが読み取りテストを通る（N1、N2）。

八つが「はい」なら、システムはこの道が要求するところまで正常化されていて、続くのはいつものはしごだ。主文書のフェーズ3と4（本番リリースと運用）はそのまま当てはまる：定期監査、マニュアル（レガシーには存在しないことが多く、第14段であるがままのシステムから生成する）、常駐エージェント、そして数字による振り返り。振り返りにはレガシー固有の質問が一つある：正常化にいくらかかったか、そして「待てる」と印した負債のうち、結局同じだけ高くついたのはどれか。

道全体の警告サイン

  • エージェントが「理解するより書き直す方が簡単だから」とモジュールの書き直しを提案する。約束のルール7の違反だ。レガシーでは、理解することが仕事だ。
  • 安全ベルトが中途半端なまま機能を変え始めた（「テスト群は後で終わらせよう」）。後では決して来ないし、テスト群なしの最初の変更こそが、誰も存在を知らなかったものを壊す。
  • 食い違いの一覧が、オーナーが一つずつ決めないまま「業務の言う通りになるようコードを直して」解決された。それらの食い違いのいくつかは、業務が忘れてコードが覚えていたルールだ。
  • 正常化のバックログが、払われる速さより速く育つ。印が間違っている：「触れたときに払う」に「待てる」ものが入っているか、負債を払わずに触れられているモジュールがある。
  • サイジングの数字が「データベースが大きすぎて数えられないから」と推定から出てきた。大きいデータベースはクエリで数える。それが計器だ。
  • 緊急の修正がループへ戻らなかった。その月に何件あったか数えること。一件より多いなら、安全ベルトはゲートではなく飾りだ。

練り上げるべき残り 仮説

  1. レガシー固有の四つの適格性の基準は、診断モードで他人のシステムに関わった私の経験から書かれている。X1とX2でしたように、断ったプロジェクトで較正してはいない。どう動くか知っている人がいないレガシーでも、データベースとコードが読めるなら成り立つかもしれない。二年誰も走らせていないテストのあるレガシーは、テストのないものより悪いかもしれない。事例が足りない。
  2. 特性化テスト群の大きさ：四つから八つのフローは小さいシステムで私にうまくいったものだ。大きいものでは、基準がフローごとなのか、モジュールごとなのか、かかっている金額ごとなのか分からない。
  3. 大きいシステムで正常化がどれだけ続くか：三週間のカレンダーはガイドプロジェクトの大きさのシステムのためのものだ。数十のモジュールがあるものでは、正常化はモジュールごとに、モジュールごとの安全ベルトで行われ、N2は丸ごと行うがN4は分割されるのだろうと疑っている。試してはいない。
  4. 方法を中途半端に使ってモデルが構築したレガシー（契約はあるがテストはない）はどうなるか：この道を丸ごと辿るのか、近道があるのか。私の直感は、近道はなく、近道こそがまさに誤りだというものだが、直感でしかない。
