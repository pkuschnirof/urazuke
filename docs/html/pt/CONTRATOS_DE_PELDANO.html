Para que serve

Não entre num projeto onde o método não pode funcionar. Se o agente não vai poder se verificar sozinho de ponta a ponta, ou se não há um dono do domínio que decida, o método se degrada em "programar com IA" e você acaba lendo código. Este degrau é a porta de entrada: cruza-se uma vez, e se não se cruza, melhor saber antes do que depois.

E uma ideia de fundo que quero que você tenha clara: o método não serve para qualquer projeto, e isso não é um defeito. Um método que promete servir para tudo não está dizendo nada. O que este degrau faz é colocar a fronteira por escrito, para que a decisão de entrar ou não entrar seja uma decisão e não uma esperança. Os dois critérios excludentes saem de projetos que recusei, não dos que aceitei Ref. 46.

1. Contexto necessário

O que segue é a lista genérica. Os arquivos concretos que você tem que ter prontos antes de cada prompt, com seu conteúdo e seu estado mínimo, estão na seção 2, no bloco "Antes de enviar o prompt" que precede cada um.

Nomeado de forma genérica; o agente avalia se basta e pede o que faltar.

  • Levantamento do pedido: o que o cliente quer, para quem, e o que acontece hoje sem o sistema.
  • Levantamento tecnológico: que tecnologia há ou se propõe, se existe um sistema anterior, se esse sistema tem repositório e como é manejado.
  • Levantamento de testabilidade: se as telas podem ser executadas por programa e se cada elemento da interface é acessível com seus diferentes métodos (clique, digitação, leitura de estado), de modo que um teste percorra a tela e verifique o efeito no backend.
  • Quem é o dono do domínio e quanto tempo tem para decidir.
  • Que consequência tem um erro (dinheiro, saúde, operação, nada).
  • Ambientes e acessos: se vai haver um ambiente de teste, se o agente pode acessá-lo, se há produção consultável em somente leitura.

A catraca e o orçamento de consultas são para sistemas com volume. O que não muda com o tamanho: nenhum número que decide algo sai de uma impressão.

Para que serve

Faça com que todo número que alimenta uma decisão saia de um programa com teste, e não de uma busca de texto, de uma impressão, nem de "acho que são uns cem". E faça com que o próprio instrumento seja auditado, porque os medidores mentem: um dos meus não via 84 chamadas com o contador em zero, e outro dizia 27 quando eram 44 Ref. 35, Ref. 36. As cinco regras que escrevi depois disso são: medidor com guarda; se o instrumento não existe, constrói-se; audita-se em duas direções; o aproximado se marca; e quem executa verifica os números de quem planejou.

Este degrau é o que mais demorei a formalizar, e por uma razão que vale a pena contar: dava por certo que um modelo aplicaria sozinho algo tão básico da engenharia como "meça antes de tocar". Não aplica. O modelo é muito bom em produzir afirmações com número ("há uns 120 laços desse tipo") e essas afirmações soam exatamente igual quando estão medidas e quando estão estimadas. Você não tem como distingui-las pelo tom. A única forma é exigir o instrumento: "com que você mediu? mostre-me o comando". Se não há comando, é uma impressão, por mais decimais que tenha. As regras, eu as impus em sessão, corrigindo o agente, antes de que fossem doutrina Ref. 45.

1. Contexto necessário

O que segue é a lista genérica. Os arquivos concretos que você tem que ter prontos antes de cada prompt, com seu conteúdo e seu estado mínimo, estão na seção 2, no bloco "Antes de enviar o prompt" que precede cada um.

  • A hipótese, sua ou do agente: "acho que o problema é X", "devem ser uns cem".
  • Acesso ao que se quer medir: o código, o banco em somente leitura, o log.
  • Os medidores que já existem no repositório, se houver.

2. Prompts

Inicial:

Antes de enviar o prompt, isto tem que existir, e quem faz é você (ou o negócio com você), não o agente:

  • A hipótese, escrita numa frase, sua ou tirada do agente: "acho que a agenda faz uma consulta ao banco para cada consulta que mostra", "devem ser uns cem laços". Vai no buraco [X] do prompt, e a quantidade a medir no outro buraco.
  • Acesso ao que se vai medir: o código (ele já o tem); o banco em somente leitura, se a medida é sobre dados reais, com a string de conexão fora do repositório e o nome da variável dito no chat; o log, com o seu caminho.
  • Os medidores que já existem no repositório, se os há, nomeados, para que o agente os reutilize em vez de fazer outro.
  • Um caso conhecido para o teste do medidor: uma situação em que você sabe a resposta de antemão ("com zero consultas tem que contar exatamente as duas consultas base ao banco"). Se não lhe ocorre nenhum, peça ao agente que o proponha, mas valide-o você: um medidor verificado contra um caso que o próprio medidor inventou não está verificado.
  • Estado mínimo aceitável: a hipótese cabe numa frase e há um caso conhecido com o qual verificar o instrumento.

Before building anything, we are going to measure. The hypothesis is: [X]. Write a meter (a script that lives in the repository) that measures [the quantity], and a test for the meter that checks it against a known case where the answer is known in advance. If measuring requires access or data you lack, ask me; do not approximate silently. If some part can only be approximated, mark it as approximate and tell me the margin. Run the meter, show me the number together with the command that produces it, and audit it in both directions: from the code to the measurement (is everything that should be counted, counted?) and from the measurement to the code (does everything counted actually exist?). Only then propose what to build. Reply in my language.

Antes de construir qualquer coisa, vamos medir. A hipótese é: [X]. Escreva um medidor (um script que vive no repositório) que meça [a quantidade], e um teste para o medidor que o verifique contra um caso conhecido onde a resposta se sabe de antemão. Se medir exige acesso ou dados que você não tem, peça-me; não aproxime em silêncio. Se alguma parte só pode ser aproximada, marque-a como aproximada e diga-me a margem. Rode o medidor, mostre-me o número junto com o comando que o produz, e audite-o nas duas direções: do código à medição (está contado tudo o que deveria ser contado?) e da medição ao código (existe de verdade tudo o que foi contado?). Só então proponha o que construir. Responda no meu idioma.

O que estou pedindo, cláusula por cláusula: o medidor no repositório (não um comando solto que se perde); o teste do medidor contra um caso conhecido (a guarda); a cláusula de completude na sua forma para medir (pedir o acesso, não aproximar em silêncio); marcar o aproximado com sua margem; o número com o comando que o produz, para que você possa rodá-lo; a auditoria em duas direções, que é o que desmascarou os meus dois medidores que mentiam; e a ordem: primeiro medir, depois propor.

Quando há um orçamento:

Antes de enviar o prompt, você tem que ter isto à mão:

  • O número medido, que você mesmo rodou com o comando que o agente lhe deu, e que deu o mesmo. Se você não o rodou, não fixe um orçamento sobre ele.
  • A margem que você está disposto a dar, decidida por você: um pouco mais do que o medido, não o dobro "por via das dúvidas".
  • Estado mínimo aceitável: você rodou o medidor.

Set the budget for [queries / loops / time] on this path at the measured value plus a small margin, and protect it with a test that fails if it is exceeded. Tell me the number and the margin.

Fixe o orçamento de [consultas / laços / tempo] neste caminho no valor medido mais uma margem pequena, e proteja-o com um teste que falhe se for superado. Diga-me o número e a margem.

O que estou pedindo: que o orçamento seja o medido mais pouco, não um número redondo, e que tenha um teste que falhe se for superado. Assim uma regressão de desempenho aparece na bateria e não em produção Ref. 37.

Quando quem planejou deu números (regra cinco):

Antes de enviar o prompt, você tem que ter isto à mão:

  • Um plano do agente com números dentro ("há 121 laços", "são 27 consultas"), à vista na conversa.
  • O medidor que mede essa quantidade, já existente (o prompt inicial deste degrau). Se não há medidor para esse número, primeiro o prompt inicial e depois este.
  • Estado mínimo aceitável: para cada número do plano você sabe com que medidor se verifica.

Before executing the plan, verify every number the plan asserts with the meter. If any does not match, stop and tell me; do not execute on a wrong number.

Antes de executar o plano, verifique com o medidor cada número que o plano afirma. Se algum não bate, pare e diga-me; não execute sobre um número errado.

O que estou pedindo: que quem executa não confie nos números de quem planejou, mesmo que seja o mesmo modelo em outra sessão. No meu caso, três de quatro afirmações do plano estavam erradas; onde havia instrumento, o número era exato.

3. Resultado esperado

  • O medidor no repositório (tools/measure_*.py, scripts/meter-*.mjs ou similar), com seu teste.
  • O número, com o comando que o produz e a data.
  • A auditoria em duas direções, escrita em duas ou três linhas.
  • O aproximado marcado como tal, com sua margem.
  • Se há orçamento: o valor, a margem, e o teste que o protege.
  • No commit: "measured: [number] with [meter]".

4. Verificação de completude

  • Você consegue rodar o comando do medidor e dá o mesmo número? (Você roda; não precisa entendê-lo, só executá-lo.)
  • O medidor tem teste? Contra que caso conhecido?
  • Há algum número no relatório sem medidor por trás? Pergunte de onde saiu.
  • O aproximado está marcado?
  • Se o plano trazia números, o agente os verificou antes de executar e lhe disse quais não batiam?

5. Sinais de alerta

  • Um número mudou entre dois relatórios sem que o código mudasse. Um dos dois não foi medido.
  • O medidor dá zero. Quase nunca é zero; quase sempre o medidor não está vendo algo.
  • O agente propõe construir "enquanto mede", para ganhar tempo. A ordem é o método: primeiro o número, depois o plano.

Passo 8 — Testes como cadeados, provados em vermelho (contrato do degrau)

Fase: ciclo. Quando: com cada pendência, ao fechá-la: o teste em vermelho e em verde, a regressão das vizinhas e o teste de ponta a ponta do fluxo tocado. A bateria completa de ponta a ponta de todos os fluxos, no fechamento de cada bloco e antes de cada implantação em produção. Forma: um disparo; o agente executa e relata, você lê o relatório. Tamanho: obrigatório em todo projeto. É o coração do método: se há um degrau que não se pode negociar, é este.

Para que serve

Um teste que você nunca viu falhar, você não sabe se prova algo. A regra aqui não é "escreva testes": é "demonstre que o teste fica em vermelho contra o código antigo, e depois em verde com o novo". Evita os testes que passam porque não provam nada, e o verde que esconde um bug Ref. 44.

Por que isto é mais importante com um modelo do que com um programador humano: o modelo escreve o código e o teste na mesma sessão, com o mesmo entendimento. Se entendeu mal o pedido, o teste vai provar o que ele entendeu, e vai passar. O vermelho contra o código antigo é a única forma barata de comprovar que o teste está olhando o que importa: se o código antigo o passa, o teste não distingue o antes do depois, e então não serve. O caso que melhor mostra isso é o dos contadores que não coincidiam Ref. 26.

Há uma objeção séria a este degrau, e quero deixá-la escrita porque vão usá-la contra: o mesmo agente que escreve o teste e o código pode fingir o vermelho. Um estudo publicado em agosto de 2026 mediu que, quando se pede a um agente o ciclo de teste primeiro, às vezes ele pula o vermelho, relata-o sem tê-lo rodado, ou implementa antes do teste para que passe de primeira (está na Parte F do documento principal, a dos trabalhos relacionados). A minha resposta tem três peças, e as três estão na escada. A primeira, aqui: o vermelho não é um relato, é um recibo: o comando exato, o identificador da versão contra a qual rodou, a quantidade de testes que falham e o código de saída, tudo colado tal como saiu, de maneira que você possa voltar a rodá-lo com um único comando sem entender o que ele faz. A segunda, no degrau 13: a auditoria por outra sessão volta a rodar uma amostra desses recibos. A terceira, no degrau 9: os testes de mutação, que plantam erros de propósito e contam quantos os testes capturam; é a única medida que, nesse mesmo estudo, distinguiu os testes que vigiam dos que decoram.

E a segunda metade: os testes de ponta a ponta. Um teste que verifica desde a tela (clica, digita, lê) e comprova o efeito no backend (a linha ficou, o estado mudou) é o que substitui a sua leitura do código. Os critérios de aceitação da pendência ("dado, quando, então") são o seu roteiro. E rodam três vezes em três escalas: o fluxo tocado com cada pendência, todos os fluxos no fechamento de cada bloco, e todos os fluxos com a versão exata antes da produção.

1. Contexto necessário

O que segue é a lista genérica. Os arquivos concretos que você tem que ter prontos antes de cada prompt, com seu conteúdo e seu estado mínimo, estão na seção 2, no bloco "Antes de enviar o prompt" que precede cada um.

  • A mudança já implementada (por padrão os testes vêm depois de implementar; "primeiro o teste" fica como opção para escopos pequenos e bem definidos).
  • A pendência que origina a mudança, com seus critérios de aceitação e seu "como se verifica".
  • A bateria existente e o comando para rodá-la (degrau 4).

2. Prompts

Rotina (vai no contrato de convivência; aplica-se em cada mudança):

Antes de enviar o prompt, isto tem que existir, e quem faz é você (ou o negócio com você), não o agente:

  • A pendência que está sendo fechada, com a sua especificação completa em docs/PENDING.md; em particular, seus critérios de aceitação na forma "dado, quando, então" e o seu "como se verifica", que são o roteiro do teste. Se a pendência não os tem, volte ao degrau 5 antes de pedir o teste.
  • A mudança já implementada pelo agente (o método testa depois de implementar, salvo que você escolha "primeiro o teste" para um escopo pequeno e bem definido).
  • A bateria existente e o comando para rodá-la, anotados em docs/STATUS.md (degrau 4).
  • O ambiente de teste rodando e acessível para o agente, com dados de teste suficientes para o fluxo que se toca. Se o fluxo precisa de dados que não existem (um paciente, uma consulta de ontem), carregue-os você ou peça que ele os crie como parte do teste; o que ele não pode fazer é simulá-los.
  • docs/WORKING_AGREEMENT.md, onde vai a rotina na primeira vez.
  • Estado mínimo aceitável: a especificação tem critérios de aceitação, e a bateria roda com um comando conhecido.

To close this pending item I need evidence, not your word. (1) Write the test that proves what the item asks for, following its acceptance criteria. (2) Demonstrate that this test fails against the previous code: you may temporarily revert the change, or run the test against the old version, but show me the red output as a receipt, not a summary: the exact command, the identifier of the version it ran against, the count of failing tests and the exit code, pasted as they came out, so that I can rerun it myself with one command. (3) Show me the green output with the change. (4) Run the regression suite for the neighbouring items and show me it is still green. (5) Run the end-to-end test of the flow this item touches, from the screen to the backend, and show me the backend effect. (6) Do not replace with mocks the very part you are trying to test. If testing end to end requires something you lack (data, access, an environment), ask me for it; do not simulate what you do not have. If the previous version does not have the module at all (the first block of a new project), a failure to load is not a red: prove the red by planting one deliberate defect in the function you just wrote (an inverted condition, a deleted line), show me the test failing against that defect as the same kind of receipt, with the diff of the defect, and then revert it. Finally, the commit message says "proved red against [what]" and the test counts.

Para fechar esta pendência preciso de evidência, não da sua palavra. (1) Escreva o teste que prova o que a pendência pede, seguindo seus critérios de aceitação. (2) Demonstre que esse teste falha contra o código anterior: você pode reverter temporariamente a mudança, ou rodar o teste contra a versão antiga, mas mostre-me a saída em vermelho como um recibo, não como um resumo: o comando exato, o identificador da versão contra a qual rodou, a quantidade de testes que falham e o código de saída, colados tal como saíram, para que eu possa voltar a rodá-lo com um único comando. (3) Mostre-me a saída em verde com a mudança. (4) Rode a regressão das pendências vizinhas e mostre-me que continua em verde. (5) Rode o teste de ponta a ponta do fluxo que esta pendência toca, desde a tela até o backend, e mostre-me o efeito no backend. (6) Não substitua por simulações justamente a parte que está testando. Se testar de ponta a ponta exige algo que você não tem (dados, acesso, um ambiente), peça-me; não simule o que não tem. Se a versão anterior não tem o módulo (o primeiro bloco de um projeto novo), um arquivo que não carrega não é um vermelho: prove o vermelho plantando um defeito de propósito na função que acabou de escrever (uma condição invertida, uma linha apagada), mostre-me o teste falhando contra esse defeito como o mesmo tipo de recibo, com o diff do defeito, e depois reverta-o. Por último, a mensagem do commit diz "provado em vermelho contra [o quê]" e os números dos testes.

O vermelho do primeiro bloco. No primeiro bloco de um projeto novo não há código anterior: o teste novo falha porque o módulo não existe, e essa falha não prova que o teste distingue comportamento. Por isso, quando a versão anterior não tem o módulo, o vermelho se prova por mutação: o agente planta um defeito de propósito na função que acabou de escrever, mostra o teste em vermelho contra esse defeito (o recibo leva o diff do defeito, para você ver que não foi trivial), reverte-o e mostra o verde. É um só mutante por pendente, executado e registrado como qualquer outro recibo; os testes de mutação sobre toda a base continuam sendo o reforço opcional do degrau 9. (Decisão D-037, a partir da prática Turnera: seis recibos de vermelho que só diziam "o arquivo não carrega".)

O que estou pedindo, cláusula por cláusula: (1) o teste, guiado pelos critérios de aceitação da pendência; (2) o vermelho demonstrado como recibo (comando, versão, números, código de saída), que é a cláusula que distingue este método de "escreva testes" e a que impede que o vermelho seja um relato; (3) o verde; (4) a regressão das vizinhas na mesma sessão, porque uma mudança quebra coisas ao lado; (5) o teste de ponta a ponta do fluxo tocado, com o efeito no backend à vista; (6) não simular justamente o que se testa; e a cláusula de completude adaptada a este degrau: se falta algo para testar de ponta a ponta, pedir, não simular. A mensagem de commit com os números deixa a evidência onde vive o código.

No fechamento de cada bloco e antes de cada implantação em produção:

Antes de enviar o prompt, você tem que ter isto à mão:

  • Todas as pendências do bloco fechadas com a rotina (vermelho, verde, regressão, ponta a ponta do fluxo).
  • A versão exata que vai ser promovida, identificada (número de versão ou commit) e implantada no ambiente de teste; diga-a no chat se não está em docs/STATUS.md.
  • A lista de fluxos que existem até agora, escrita por você a partir dos casos de uso da árvore semântica, para contrastá-la com o que o agente disser que cobriu. Sem a sua lista, "todos os fluxos" é o que o agente lembrar.
  • Estado mínimo aceitável: você sabe quantos fluxos a bateria tem que percorrer antes de perguntar a ele quantos percorreu.

Run the complete end-to-end suite of every flow that exists so far, in the test environment, with the exact version that will be promoted. Show me the counts, and for each flow the backend check that proves it. If any flow has no end-to-end test, say so and open a pending item for it; do not pass it as covered.

Rode a bateria completa de ponta a ponta de todos os fluxos que existem até agora, no ambiente de teste, com a versão exata que vai ser promovida. Mostre-me os números e, para cada fluxo, a verificação no backend que o prova. Se algum fluxo não tem teste de ponta a ponta, diga e abra uma pendência; não o dê por coberto.

O que estou pedindo: a segunda e a terceira escala dos testes de ponta a ponta, com a versão exata (não "a última"), com o efeito no backend por fluxo, e com a cláusula de completude: o que não está coberto se declara e vira pendência, não se dá por coberto.

Quando o agente diz que não dá para testar:

Antes de enviar o prompt, você tem que ter isto à mão:

  • A mensagem do agente dizendo que não dá para testar, lida com atenção: não dá, ou falta algo a ele? Se o que falta é um insumo que você tem (dados, um acesso, um ambiente), dê-o e não mande este prompt. Este prompt é para quando de verdade falta algo no sistema (identificadores nos elementos da tela, um modo de teste do fornecedor externo).
  • Estado mínimo aceitável: você distinguiu entre "falta-me um insumo" (você o dá) e "o sistema não é testável aqui" (este prompt).

Explain why it cannot be tested, what would have to be added so that it can, and open a pending item for that. The change is not closed until it can be tested.

Explique por que não dá para testar, o que haveria que acrescentar para que dê, e abra uma pendência para isso. A mudança não está fechada até que possa ser testada.

O que estou pedindo: que "não dá para testar" não seja o fim da conversa mas o começo de uma pendência. A não-testabilidade é dívida, e a dívida se registra.

3. Resultado esperado

  • O teste novo no repositório, nomeado com a pendência que fecha.
  • No relatório do agente e na mensagem do commit: a saída em vermelho como recibo (o comando, a versão contra a qual rodou, quantos falham, o código de saída), a saída em verde, e a regressão em verde com seus números.
  • O teste de ponta a ponta do fluxo tocado, com a evidência de que o backend mudou (a linha, o registro, o estado).
  • No fechamento de cada bloco e antes da produção: a bateria completa de ponta a ponta em verde, por fluxo, com a versão exata.

4. Verificação de completude

  • O relatório mostra o vermelho? Com números: "4 de 8 falham contra o critério antigo". Se só mostra verde, o degrau não foi subido.
  • O vermelho é um recibo ou um relato? Tem que ter o comando exato, a versão contra a qual rodou, os números e o código de saída. Uma vez por bloco, escolha uma pendência ao acaso e rode você mesmo esse comando: o vermelho tem que voltar a aparecer.
  • A regressão rodou na mesma sessão? Quantos testes, quantos em verde?
  • Há alguma parte "simulada" (mock) justo onde está a mudança? Pergunte ao agente o que simulou e por quê.
  • O commit cita a pendência e diz "provado em vermelho"?
  • O teste de tela verifica também o efeito no backend?
  • No fechamento do bloco: estão todos os fluxos na bateria de ponta a ponta, ou há algum que "se cobre com os unitários"?

5. Sinais de alerta

  • Todos os testes novos da semana passaram em verde de primeira, e nunca se mostrou um vermelho. Ou o agente está omitindo o passo ou os testes não provam nada.
  • A bateria demora cada vez mais e ninguém sabe por quê. Costuma ser que os testes de ponta a ponta foram sendo substituídos por simulações "para rodar rápido".
  • O agente relata "os testes passam" sem dizer quantos. Sempre com números.
  • O vermelho vem contado em prosa ("o teste falhou como se esperava") sem comando, sem versão e sem números. Um vermelho sem recibo vale o mesmo que nenhum.
  • Você chega à saída para produção e a bateria completa de ponta a ponta roda pela primeira vez. Faltaram os fechamentos de bloco.

Passo 9 — Qualidade do código verificada por máquina, com comporta (contrato do degrau)

Fase: ciclo. Quando: monta-se uma vez, ao abrir o primeiro bloco funcional (assim que termina o arranque), e a partir daí roda sozinho em cada commit, como comporta da integração contínua; cada pendência se fecha com a qualidade em verde, depois do teste em vermelho (8) e antes do caso de teste manual (10). No fechamento de cada bloco e antes de cada implantação, o relatório de qualidade se lê com o dono. Num legado, a primeira corrida é a linha base e os achados entram na lista de pendências com a sua marca de velocidade. Forma: um único disparo para montar; depois, rotina de cada mudança e leitura por bloco. Tamanho: obrigatório no seu nível mínimo em todo projeto (um linter e um limite de tamanho na cadeia); completo, com testes de mutação incluídos, em qualquer projeto com usuários. Os testes de mutação ficam como reforço opcional só quando não há usuários reais (uma ferramenta interna, um protótipo que mais ninguém roda).

Para que serve

O dono não lê o código, e esse é o ponto do método. Mas o código existe, alguém vai mantê-lo (o próximo agente, o próximo desenvolvedor), e um código que funciona hoje e é ilegível amanhã é dívida que se cobra no mês três. Se ninguém o lê, uma máquina tem que olhá-lo: ferramentas que, em cada commit, medem o que um revisor humano olharia e o convertem num número com um limite. Eu fiz isso em todos os meus projetos, sem nomeá-lo como degrau, e uma auditoria de qualidade me devolveu um componente de mais de duas mil linhas e um arquivo de projeto de quase dez mil Ref. 41: nenhum dos dois teria passado um limite de tamanho escrito. A catraca estática, que impede que um número de qualidade piore Ref. 35, é a forma que dou a este degrau.

O que se mede por máquina, em ordem de importância: que o código respeite um estilo único (o linter e o formatador); que nenhuma função nem nenhum arquivo passe de um tamanho; que a complexidade de cada função fique abaixo de um limite; que não haja código duplicado nem código morto; que as dependências estejam declaradas e usadas; que a cobertura dos testes nunca baixe (a catraca); e, se a linguagem permitir, que os tipos fechem. Nada disto substitui o teste em vermelho: um código impecável pode estar errado. O que evita é o código correto que ninguém pode voltar a tocar.

E a peça que deixo de tratar como reforço opcional em qualquer projeto com usuários: os testes de mutação. Passo 12 — Verificação honesta e relatório proporcional (contrato do degrau)

Fase: ciclo. Quando: em cada relatório, de cada pendência, durante todo o projeto. É a forma que tem que ter tudo o que o agente lhe diz. Forma: rotina; é a forma que cada relatório do agente deve ter. Tamanho: obrigatório em todo projeto, sem exceções. Não custa nada e é o que permite ao dono não ler código.

Para que serve

Se você não vai ler código, o relatório do agente tem que ser confiável. Não otimista, não "completo na aparência": confiável. Isto é o genuinamente novo do método: o autor do código fabrica também a evidência, e faz isso com a mesma segurança na voz quando está certo e quando está errado. Por isso a evidência tem que provar a si mesma, e o relatório tem que separar o verificado do acreditado. A regra, eu a escrevi em junho Ref. 8, e voltei a precisar dela em outubro, quando um erro de autenticação foi relatado com a legenda "success" Ref. 43.

Entenda por que o modelo tende a relatar de mais. Não é má-fé: é que foi treinado para ser útil e completo, e um relatório que diz "isto não consegui verificar" parece menos útil do que um que diz "pronto". Então peça explicitamente as más notícias, os pontos cegos e o que ele não fez. Se você não pede, ele não dá, não porque esconda mas porque não considera isso parte da resposta.

  • O relatório é mais longo do que a mudança. Um relatório proporcional diz o que há que dizer; um inflado está tapando algo com volume.

Passo 13 — A auditoria periódica como insumo do plano (contrato do degrau)

Fase: saída para produção. Quando: obrigatória antes da primeira implantação em produção; abre a fase de saída. Depois, em operação, a cada um ou dois meses segundo o ritmo de mudança, e no fechamento de cada etapa grande. Forma: um disparo longo, idealmente a um agente diferente do que constrói. Tamanho: obrigatório antes da primeira implantação em produção, em qualquer projeto; depois, proporcional ao ritmo de mudança (um sistema que muda todas as semanas se audita a cada mês; um estável, a cada seis).

Para que serve

Olhe o sistema inteiro com olhos frescos de vez em quando, e converta o que vir em pendências. A auditoria não é um relatório que se arquiva: é plano. Evita a senha escrita no código que ninguém tinha visto, as consultas que leem tabelas inteiras Ref. 18, a vulnerabilidade conhecida numa dependência, o componente de milhares de linhas Ref. 41. E é a independência do controle de qualidade levada um passo mais para dentro: quem audita não é quem construiu.

Sobre a independência: não precisa de outra empresa nem de outra ferramenta. Basta outra sessão, com outro arquivo de instruções, que não tenha participado da construção. O que você busca é que o auditor não compartilhe os pressupostos do construtor. Um modelo que construiu um módulo "sabe" que a senha hardcoded era provisória; um modelo que o vê pela primeira vez a relata como o que é. Assim se detectaram duas portas de administrador que o construtor tinha deixado num dia Ref. 40.

Se puder escolher, que seja também um modelo diferente do que construiu, não só outra sessão do mesmo: um estudo de 2026 mediu que uma sessão limpa com um modelo diferente encontra mais erros que duas sessões do mesmo modelo (arXiv 2610.01471). Não é uma comporta dura, porque às vezes o modelo do construtor é o único disponível; é uma preferência que vale a pena exercer quando se pode, e quanto mais crítico o sistema, mais vale exercê-la.

Passo 14 — Fail-closed, cadeados e zero dano silencioso (contrato do degrau)

Fase: saída para produção. Quando: na fase de saída para produção, ANTES de construir qualquer funcionalidade que cobre, envie, aprove ou apague; revisa-se com cada ação nova com consequências. As automações novas começam em modo de ensaio e se habilitam depois de olhar seu registro por uns dias. Forma: conversa: o agente lista as ações com consequência, você confirma quais levam cadeado e de que tipo. Tamanho: obrigatório assim que o sistema faz algo irreversível (cobrar, enviar, apagar, aprovar). Um sistema de somente leitura pode pulá-lo; no momento em que ganha seu primeiro botão que age sobre o mundo, este degrau passa a ser o mais importante.

Para que serve

Faça com que o sistema, diante de uma dúvida ou de uma falha, NÃO aja, e que o diga. Soa óbvio e é o contrário do que o software faz por padrão, que diante da dúvida segue em frente. Evita a dupla cobrança, a aprovação automática sem passar por um humano, o git add -A que sobe uma credencial, e o apagamento de dados do cliente. Os cadeados que coloquei no Plano de Saúde são o modelo: o botão de pânico com dupla trava, o aprovador automático em modo de ensaio, o vigia com guardas Ref. 28; e o reflexo de que uma falha deixe uma linha sem seu botão em vez de quebrar a listagem inteira Ref. 25.

O princípio tem nome, "fail-closed", e vem da segurança física: uma porta de segurança que fica fechada quando a luz acaba. O contrário, "fail-open", é a porta que se abre. Em software a maioria das coisas é fail-open por padrão: se a validação falha, o código segue; se o serviço não responde, assume-se que está tudo bem. O método inverte o padrão: na dúvida, não. E se aplica tanto ao sistema quanto ao agente que o opera.

3. Resultado esperado

  • Coleta de recursos e tempos de resposta com história, sem dados pessoais.
  • Alertas por limiar e por desvio, para um canal que uma pessoa lê.
  • O relatório cíclico, gerado sozinho, com cada desvio causado ou proposto.

5. Sinais de alerta

  • Os alertas disparam todos os dias e ninguém os lê. É preciso baixar a sua quantidade até que cada um signifique alguma coisa, não se acostumar.
  • O relatório diz "tudo normal" três ciclos seguidos. Ou o sistema não tem usuários, ou o relatório não olha o que importa.
  • Um limiar subiu "para que pare de avisar". É o degrau 21 morrendo em silêncio.
  • O monitoramento guarda dados pessoais "para poder diagnosticar". É um vazamento com horário.

Passo 22 — Monitoramento de erros e relatório cíclico: nenhum erro sem pendência (contrato do degrau)

Fase: operação. Quando: monta-se na fase de operação, com a primeira implantação, junto com o 21, sobre os registros do 16; a partir daí roda sozinho, com alertas na hora e um relatório cíclico que se lê com o dono. Cada erro novo entra no ciclo como pendência corretiva e se fecha com o teste que o reproduz em vermelho. Num legado, a primeira leitura é a linha base: os erros que já existiam no primeiro dia viram pendências com a sua marca de velocidade, e nenhum fica como "conhecido" sem uma pendência que diga por que se tolera e até quando. Forma: um único disparo para montar; depois, rotina cíclica. Tamanho: obrigatório em todo projeto com usuários: a captura centralizada e o relatório não se negociam; os alertas na hora, proporcionais.

Para que serve

Um sistema em produção produz erros que nenhum usuário reporta: o que viu a tela em branco e tentou de novo, o da tarefa noturna que falhou e ninguém olha, o da chamada externa que devolveu um erro e o código engoliu. Se não os capturo, não existem até que existam demais. Este degrau é a contraparte do 21: aquele vigia o desempenho, este vigia os erros, e os dois terminam no mesmo lugar, o ciclo, como pendências corretivas. As regras de fundo são duas. Nenhum erro sem pendência: um erro novo abre uma, e se fecha com o teste que o reproduz em vermelho, como pede o modo corretivo do caminho evolutivo. E não existe o "erro conhecido" sem uma pendência que diga por que se tolera e até quando; "esse erro sempre esteve aí" é a frase com que um sistema apodrece. O erro de autenticação reportado como sucesso Ref. 43 e as quatro rodadas até a causa raiz Ref. 22 são os dois antecedentes: o primeiro, de que os erros se escondem se não forem capturados por máquina; o segundo, de que um erro sem reprodução se corrige várias vezes.

Se você está começando. Um erro é qualquer coisa que o sistema tentou fazer e não conseguiu: uma tela que não carregou, uma tarefa noturna que se interrompeu, uma chamada a outro serviço que falhou. Uma exceção não tratada é um erro que o código não previu e que corta o que estava fazendo. Capturar um erro é guardá-lo com todos os seus dados (quando, em que versão, com que identificador, a pilha, que é a lista de passos do programa até a falha) num único lugar central, em vez de deixá-lo se perder na tela de um usuário. Agrupar é juntar as mil vezes que aconteceu o mesmo erro numa só entrada com um contador. E a taxa de erro por fluxo é, de cada cem vezes que alguém cadastrou um turno, quantas falharam.

  • A observabilidade (16): os erros chegam com identificador de correlação, versão e ator.
  • A tabela de cadeados (14): os erros em ações com consequência são alerta imediato.
  • Produção implantada (15), com o navegador do usuário incluído na captura.
  • O canal de alertas e o ciclo do relatório, compartilhados com o 21.

  • Captura centralizada de erros no backend, nas tarefas e no navegador, agrupados por causa, sem dados pessoais.
  • Alertas por erro novo, recorrente que cresce, e com consequência.

Passo 23 — O agente dentro do sistema, e a retrospectiva com número (contrato do degrau)

Fase: operação. Quando: o agente residente, ao entrar em operação, depois da primeira implantação em produção. A retrospectiva, no fechamento de cada etapa e do projeto; volta ao degrau 0 para o projeto seguinte. Rode também uma retrospectiva curta quando mudar o modelo que constrói: um contrato calibrado para um modelo não necessariamente rende igual com outro, e a mudança de modelo é exatamente o tipo de achado que esta escada pede para virar uma proposta de mudança, não uma surpresa descoberta no meio de um bloco. Forma: duas partes: uma conversa para definir o escopo do agente residente, e um disparo longo para a retrospectiva. Tamanho: o agente residente é opcional (muitos sistemas não precisam dele; os que têm usuários que pedem suporte, sim). A retrospectiva é obrigatória em todo projeto, mesmo que seja de uma página: sem ela o método não aprende.
