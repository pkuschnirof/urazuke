What this is, and why it lives here

The mechanical definition of the gates of the method -- which artifact has to exist at each step, what it has to say, and with which strategy it is verified -- used to live compiled inside the tool that enforces it. Which meant it changed when the tool shipped a version, not when the method decided. Since decision D-050 the method owns the definition and publishes it as data, exactly as it already publishes the prompts, and the tool consumes it.

The version: what a project freezes

What a project pins, and what it costs to change it. A project pins ONE catalog_version the day it starts and keeps it until the end. That is not convenience: raising the version in the middle of a project is a REGRESSION of the completeness state, because a version that adds a requirement to a step already closed reopens that step, and what was green yesterday is not green today. Raising it is allowed and it is the owner decision, written with its date in the project decision record; what is not allowed is raising it in silence, or discovering mid-project that the gate is measuring against a definition nobody chose.

For that to be possible, what is published has to be identifiable and stable:

  • catalog_version (2026.10.9): declared by hand by the method. It is what a project freezes, and what has to read back the same two years from now.
  • content_hash (sha256): computed by the build over the enforceable content, with the keys sorted and without the publication metadata. The consumer recomputes it and compares: if it only read it, a frozen copy edited by hand or truncated by a merge would be undetectable.
  • git_commit: informative, and no comparison looks at it. The identifier a build can know about itself is always the one of the change before the change that contains it, because it is computed before saving; it is useless as the identity of what is published.

Covered by the fingerprint: schema_version, catalog_version, languages, evaluators, evaluator_semantics, compatibility, tramos, steps, stations, loop_entry, heuristics, adapters, project_config, counts, what, pinning. Left out: generated_at, git_commit, git_commit_note, source, license, content_hash. Nothing in between: Every key of the published payload is either covered or excluded, and the validator checks it. A requirement-bearing key left out of both would travel without protection: a frozen copy could be altered there and the recomputed hash would still match.

When the version moves: Any change to a key listed in hash_covers raises catalog_version, even when no requirement changed: the content hash moves with it, and two different contents published under one declared version would make a freeze unreadable. A regeneration that only rewrites generated_at or git_commit changes nothing covered, so it leaves the version alone.

The ledger: gates/catalog.json#changelog records, for each catalog_version, the content hash it produced. The build refuses to publish when the hash of the current content is not the one recorded for the current version: that is what forces the bump instead of trusting it. The ledger is append-only and a hash already recorded is never edited, for the same reason the base is not edited. It is not part of the published payload, so recording a new entry cannot change the hash it records.

Pinning: what a tool that freezes the method owes

The pair a project freezes: catalog_version, content_hash.

  • It records: A tool that pins records, in whatever it writes for the project, the catalog_version it pinned and the content_hash that version declares. Those two, by those names.
  • It contrasts: It contrasts that pair against the version ledger: an append-only record of (declared version → content hash) that lives in the method repository and not on the host that served this file, so the pair can be checked against a second source. Its address is published per resource by the index of this data interface, under resources[].version_ledger: url is the page a person reads and fetch_url is the same file as JSON, which is the one a tool downloads. Read both from the index; do not derive one from the other and do not hardcode either, because a derived address is an invented address. Written this way on 2026-10-27: the first wording of this clause pointed the consumer at a key of the sources that no published payload carries, and the index declared only the human page, so the one consumer that implemented the obligation had to guess the address it downloads (PND-056).
  • On a mismatch: Red, and it says which of the two moved: the content under a declared version, or the version under one content. Never green, and never a silent re-pin to whatever the host is serving today.
  • Forbidden: Pinning to an internal compiled identity that the method cannot name. It looks like pinning and it is not: nobody outside the tool can audit it, and the differential against a published version cannot be computed, so the project cannot be told what an upgrade would reopen.
  • Why it is written: Measured on 2026-10-27: a consumer that already pinned, and pinned correctly in its own terms, pinned to an identity of its own that is not a catalog_version and appears in no ledger. The data said what to freeze and never said what to freeze it BY.

Raising the version. Who decides: owner.

  • Before deciding: Compute the differential and show it: which requirements enter between the pinned version and the candidate, and which steps they anchor. A project is told what an upgrade reopens before it is raised, not after.
  • How the differential is computed: Every entry the method added after the freeze declares since_version. An entry with no since_schema comes from the frozen base and is present in every published version. So the differential between a pinned version X and a candidate Y is every entry whose since_version is greater than X and not greater than Y; it needs no network beyond the two files.
  • What a newly required evaluator means: An installation that cannot measure a required evaluator reports declared and not measured, and the step does not advance (see compatibility). That is the mechanism by which an upgrade stops a project, and it is the intended behaviour, not a defect.
  • Every covered key has existed since 2026.10.1. Every top-level key the fingerprint covers has existed since the first version the method published, so no consumer can hold a pinned version that is missing one of them. A key added later records its arrival in the ledger entry of its version.

A prior version. The canonical URL serves current_only.

  • The canonical URL serves the current version only. The content of a prior version is in the method repository: the ledger gives the pair (version → content hash) and the published file is committed there, so searching that history for a recorded hash finds the commit that published that version.
  • Not guaranteed: There is no per-version URL on this host today, and saying so here is cheaper than letting a consumer discover it. A tool that needs to re-read the exact content it pinned reads it from its own frozen copy; the fingerprint is what tells it the copy is intact.

The language of each text

Which language each human-readable text of this file is in. It is declared mechanically because the file is bilingual: reading data as a single language would make a consumer show Spanish to an English reader.

  • Declared: languages.data = mixed, default en.
  • Spanish scope: tramos, steps, stations, loop_entry, told apart by since_schema.
  • Rule: Inside the keys listed in spanish_scope, a text is Spanish when neither its own node nor any enclosing node declares since_schema >= 2: it comes from the frozen base, and the base is not edited. A node with since_schema >= 2 is new, and its text is English. Every text outside spanish_scope is English.
  • Readable text fields: title, summary, verify, label, text, note.
  • Ids, step and station keys, evaluator names, enum values, file paths and the regular expressions of must_contain / should_contain are not prose and carry no language. The regular expressions are deliberately bilingual, so that a gate matches a document written in either language.
  • The method checks this declaration on every build: every text the rule calls Spanish has to appear literally in gates/baseline.json, and no text the rule calls English may read as Spanish. If the declaration stops being true, nothing is published.
  • For a consumer: Do not print these texts to an end user. Read the stable id -- an opaque key that is never translated -- and take the text from your own catalogue. That holds for the English texts too: this file is the definition of the gates, not a translated user interface.

What an installation cannot measure

  • Unknown evaluator, required: The installation does NOT report green. It reports "declared, not measured by this installation", naming the evaluator, and the step does not advance.
  • Unknown evaluator, not required: A warning: it names it and the step may advance.
  • Forbidden: Approximating with the closest evaluator, or ignoring the block. Zero silent damage.

The evaluator vocabulary

An evaluator is the strategy a tool uses to decide whether a step is fulfilled. The vocabulary is closed and only grows: none is removed, none is renamed and none changes meaning, exactly like a stable error code.

evaluatorsince schemawhat it checks
artifacts1Every declared artifact exists, passes its min_bytes, satisfies each must_contain and, if it is a glob, the newest one is within its fresh_days. A should_contain that does not appear leaves a warning, not a red.
sizing1The artifacts, plus an admissible sizing record: volumetry, retention per data class and hardware envelope, all declared by the owner.
ci1The artifacts, plus a continuous integration definition that exists in the repository.
pendings_spec1The artifacts, plus every open pending item carrying its full specification (acceptance criteria and how it is verified). An empty plan is red, not green.
receipts1The artifacts, plus evidence receipts including at least one proven red and one green. No receipt, no step.
reports1The artifacts, plus every closed pending item having its honest report (verified / believed / blind spot). No closure yet is red, not green.
meters1A meter exists in the repository and the meter has a test of its own.
owner1Nothing mechanical: the owner verifies it and signs it. No step of the catalogue chooses it today; the state exists for a step that leaves no machine check at all, and that is why the name is published anyway.
heuristics2The Annex H rule catalogue is declared and active per group; every active rule has an instrument, a severity and a checker; every switched-off rule has its record with reason, author and review date (switched off without a record is red, not the absence of a rule); every undeclared threshold is reported as undeclared instead of invented; and the report emits the two figures with the ruleset fingerprint. A switched-off group is never read as fulfilled.
profile_matrix2The functionality-by-profile matrix exists and is consistent: every functionality has at least one profile, every profile has at least one functionality and its entry point, and navigation is derived from the matrix rather than hand-written. And for every profile, the end-to-end test compares what is reachable against its row: neither less nor more.
manual_cases_per_profile2Every manual test case was run once per affected profile, derived from the matrix. A case run with a single profile does not count as executed.
pendings_profiles2Every pending item that touches a screen declares its functional convergence group, the profiles that have it and one acceptance criterion per profile. Without that declaration the pending item does not pass the step.

Annex H: 46 rules

The statement of every rule lives only in Annex H: it is extracted from there on every build, never transcribed. The published statement comes from the English version; the Spanish one is the source of truth of the method, and the build demands that both carry the same rules with the same severities. What this data adds is the mechanical part: the group, the instrument, the initial severity, when it is looked at and the step where it hooks. There are 18 of code quality and 28 of usability.

The two switches (code_quality and usability) are turned on and off separately, they live in the project configuration and the gate reads them: never inside the prompt. Switching a rule off is valid only as a recorded decision with reason, authorized_by, review_date. Switched off without a record: red: switching a rule off without a written reason is a failure of the gate, not the absence of a rule. A switched-off group is never read as fulfilled.

Ruleset fingerprint on every record: catalog_version, rules_active, rules_switched_off, adapter, tool_versions. Ratchet over compliance: it goes down only with a recorded decision. Out of the percentage, because a person judges it: UX-06, UX-07, UX-27, every manual case. The scoreboard does not close blocks, and an invalid ruleset emits no figures at all.

Order in the step 12 report: binary verdict → the two figures → what is switched off and until when → movement against the previous block with its cause.
