开始之前

这一部分是给谁的

给那些做完第一部分、然后发现在现实生活里几乎没人会给你一个空文件夹的人。给你的是一个已经在跑的系统，有依赖它的用户，然后让你"把这个修一下"或者"给它加上那个"。也给那些几个月前"凭感觉写" 了点什么、它居然能用、而现在必须在它上面继续构建又不能让它塌掉的人。这两种人站在同一个地方：面对一个遗留系统，哪怕其中一个是自己写的。

结束时你会拥有什么

还是你继承来的那个系统，做着它一直在做的事，但是方法所预设的一切都在它周围了：一份带遗留规则的协作契约、一张从系统里恢复出来的地图（每条断言都标着它从哪里来）、一份"代码做的事"和"业务以为的事"之间的不一致清单、一份变成了带速度标记的待办队列的审计、一个带匿名化数据的测试环境、一条重复得了的部署链、代码之外并且轮换过的密钥、一套看守关键流程的表征测试套件、给那些已经作用于现实世界的东西上的锁、用测出来的数字做的容量估算，以及一条债务和客户请求按模块配对住在一起的待办队列。再然后，第一个带着红色测试被纠正掉的 bug，和第一个用完整方法构建出来的新功能。

这一部分的顺序

阶段课你还要做什么
1N0、N1、N2、N3阅读。 什么都不改。你和所有者一起走一遍恢复出来的树，一条一条地决定那些不一致，读审计。收尾时：地图和债务清单。
2N4、N5安全带。 带匿名化数据的测试环境、部署跑两遍、密钥轮换、带变异红的表征测试套件。对已经作用于现实世界的东西确认锁。收尾时：系统在测试环境里跑起来，测试套件是绿的。
3N6、N7、R1测量、排序、纠正。 测出来的容量估算。带两个标记的待办队列。第一个功能块：那个已知的 bug，以纠正模式连同它的配对项一起关闭。
4R2演进。 第二个功能块：新功能，用完整的方法构建（第一部分的第 5 到 12 课），用表征测试作回归。
5 和 6第一部分的 13、14、15、20、16、17、18、19上线生产。 定期审计、剩下的锁、通往生产之路的收尾、三份手册（遗留系统本来没有），以及部署之前的四级运维质量台阶：完整的可观测性、用 N6 测出来的东西做的持久化、作为闸门的漏洞扫描、带断裂点的负载测试。
7第一部分的 23、21、22运维。 两个监控随部署搭起来，第一次阅读作为遗留系统的基线；驻留代理；带着遗留系统专属问题的复盘：规范化花了多少成本。

引导项目："继承来的 Turnera"

还是第一部分里那家诊所，两年之后，而且在另一条时间线上：他们从来没有用方法做过 Turnera。取而代之的是，负责人的侄子在一个夏天给他们做了一个网页应用 "Turnos"，从那以后一直在用。今天有两名前台和三名专业人员每天在用它，登记了大约两万个预约，而没有一个人完整理解它：侄子搬到国外去了，两周回一次消息。

现有的东西。 一个 GitHub 仓库，里面是代码（只有一个分支，提交信息都是"修了点东西"之类），一个和应用跑在同一台服务器上的数据库，靠 FTP 复制文件的手工部署，数据库密码写在代码里，没有任何测试，服务器上有一个每天晚上发送提醒的定时任务，还有一张负责人每个月用一个桌面工具连数据库下载下来的表格。有一个"自动"备份，从来没人恢复过。

哪里疼。 两件事。第一件是一个 bug：有时候一个患者会收到两次提醒，有时候一次都收不到；负责人不知道什么时候会发生，但她有患者抱怨的截图。第二件是缺的东西：他们想对某些预约通过支付链接收一笔定金，还想不用下载表格就能看到这个月有多少预约、多少爽约、多少取消。

所有者。 还是那位负责人：对业务有判断力，每天十五分钟，不读代码。还有一个很重要的新情况：她以为系统会做一些它其实不做的事，而系统真正做的一些事她并不知道。这在遗留系统里很正常，也正是第 N2 课要揭开的东西。

关键流程，用她的原话："我登记一个预约"、"我取消一个预约"、"提醒送到了"、"我找一个患者"、 "我下载这个月的表格"。五个；它们将成为表征测试套件。

这些就够了。其余的一切都在系统里，而要去读它的是代理。

规范化阶段：第 N0 到 N7 课

这八节课就是第一部分没有的那个阶段。头四节是阅读课：什么都不改，而想改点什么的冲动会非常大。接下来两节造安全带。最后两节测量和排序。再之后才碰功能。

第 N0 课 — 既有系统的适格性：由代理做出来验证的前提条件

你需要理解什么。 在第 0 课里，那些准则是由调研来回答的。这里有一个系统，于是那些准则可以 靠做来验证，由代理来做，不需要谁发表意见：它能不能搭起一套带源码、数据和持久化的完整环境？它能不能理解这份代码？它能不能只凭代码写出一份描述全部功能、而且负责人认得出那是她的系统的文档？它能不能用一个测试工具操作那些界面并跑一条端到端测试？它能不能用今天的工具构建出来？数据能不能被复制并匿名化，有没有一份恢复过的备份？那些集成有没有测试模式？一共七条前提条件，而新规则是：一条红的不是"不可行"，它是一个前置项目，有它自己的范围，好让这个系统变得适格。

发送提示词之前，用你自己的手：

  • docs/INITIAL_SURVEY.md，简短的：按负责人的说法，Turnos 做什么、给谁用；哪里疼（提醒发两次、缺的东西）；谁做的、他多久回一次话；它在哪里运行；谁有访问权；还有有一个"自动"备份从来没人恢复过。半页。
  • docs/ELIGIBILITY_CRITERIA.md：第 0 课的卡片，再加遗留系统的那七条前提条件（从演进-纠正之路那一页的 N0 站点抄过来），带三列空白：绿或红、证据、前置项目。
  • 给代理的仓库读访问权、一份数据库副本（或者生产环境的只读访问权），以及一个让代理可以尝试把系统跑起来的地方（对课程来说你自己的机器就够了），凭证放在聊天之外。
  1. 把 N0 站点的初始提示词（在演进-纠正之路那一页）原样贴给它。
  2. 它会花些时间：它得搭环境、把一切读完、写出 docs/FUNCTIONALITY_RECOVERED.md，还要跑一个测试。它做完之后，和负责人一起读那份文档：它描述的是她以为自己拥有的那个系统吗？对不上的地方记下来：那是第一份不一致清单。
  3. 看那张卡片：每条前提条件都必须有代理做了某件事的证据，而不是你给出的一个回答。

发送提示词之前（收尾提示词）：你的决定，一行话，以及对每一条红的，那个前置项目是现在做、以后做，还是永远不做。

  1. 粘贴 N0 站点的收尾提示词。

完整性检验。 每条前提条件都有做出来的证据，而不是说出来的吗？功能恢复文档存在吗，负责人认得出它吗？它跑过一条真实的端到端测试吗？每一条红的都有它的前置项目作为阻塞待办项吗？

交付物。 docs/ELIGIBILITY.md、docs/FUNCTIONALITY_RECOVERED.md，以及那些前置项目的阻塞待办项（如果有）。

常见错误。 接受一个代理没做就回答出来的绿（"是的，代码是能看懂的"）。还有把一条红当成拒绝：方法要的是一个前置项目，不是一次放弃。

在引导项目中。 代理用一份数据库副本在你的机器上把 Turnos 搭了起来（绿），它看得懂代码，只有一个用老模板语言写的报表模块除外（绿，附注），它写出了功能文档，而负责人在里面发现了两件她不知道系统会做的事（绿：这份文档比她的记忆更好），它操作了六个界面里的四个并跑了一条登记流程的测试（红：两个界面不可操作，前置项目："让日历和搜索变得可操作"），它用今天的工具构建了出来，只有 PDF 生成器的一个死掉的依赖除外（红：一个小的前置项目），它复制并匿名化了数据（绿），但那份备份从来没有恢复过（红：恢复它是所有前置项目里最便宜的一个），而消息服务商有测试模式（绿）。决定：可行，在三个前置项目之后。

第 N1 课 — 遗留系统的协作契约

你需要理解什么。 在第 1 课的六条规则之上再加五条，它们之所以存在，是因为一个模型面对别人的代码会条件反射地做三件事：重排它，在它觉得不对的地方"修"它，以及认定代码里和它预期不一样的东西就是错误。遗留系统的规则挡住这些反射：不重构没被要求的东西，动之前先读，怪事只记不修，当前行为就是规格直到所有者另有说法，以及表征测试不绿就什么都不许进。

发送提示词之前，用你自己的手：

  • 你的工作偏好，和第 1 课一样，再加一个决定：规范化期间你接受多大风险。课程里这样定：代理可以自己部署到测试环境；到生产环境永远不行，直到第 15 课。
  • docs/ELIGIBILITY.md 已关闭。
  1. 粘贴这条提示词：

Before we touch anything, we are going to set the working agreement between you and me for a system that already exists and has users. Write docs/WORKING_AGREEMENT.md with the six rules of the method (my time is sacred; zero technical debt; exact scope; documentation in the same commit; never report as done what you have not verified; speak my language), each with one line explaining what it prevents, and these five rules for an inherited system: (7) Nothing is refactored that was not asked for, and no module is rewritten. (8) Code you do not understand is read before it is touched, and what you learn goes into the system map. (9) Anything strange you find (a secret in the code, a dead path, a duplicated rule, a query without an index) is logged as a pending item with its evidence, never fixed in passing. (10) Current behaviour is the specification until the owner says otherwise: a difference between what the code does and what the business says is a discrepancy for me to decide, not a bug for you to fix silently. (11) No change reaches the test environment without the characterization suite green. Add any rules you think this system needs, marked as proposals. If you need to know something about how I work in order to write this, ask me.

在我们动任何东西之前，要为一个已经存在、而且有用户的系统，定下你和我之间的协作契约。写 docs/WORKING_AGREEMENT.md，包含方法的六条规则（我的时间是神圣的；零技术债务；精确的范围；文档在同一次提交里；绝不把没验证过的东西报告为已完成；说我的语言），每条附一行说明它避免了什么，再加上这五条针对继承来的系统的规则：（8）不重构任何没被要求的东西，不重写任何模块。（11）你不理解的代码，先读再动，而你学到的东西要进系统地图。（7）你发现的任何怪事（代码里的一个密钥、一条死路径、一条重复的规则、一个没有索引的查询）都作为带证据的待办项记下来，绝不顺手修掉。（12）当前行为就是规格，直到所有者另有说法为止：代码做的事和业务说的事之间的差异，是一条由我来决定的不一致，不是一个由你悄悄修掉的 bug。（13）表征测试套件不绿，任何改动都不许进测试环境。你认为这个系统还需要什么规则，就加上，标为提案。如果你需要知道我是怎么工作的才能写出这份契约，就问我。

  1. 读那些提案。如果有一条写着"随着触及逐步把代码现代化"，带着理由拒绝它：那是伪装起来的重写。

发送提示词之前（收尾提示词）：你对每条提案的裁决，各附一行理由，用来填提示词的空。

  1. 用第 1 课的收尾提示词收尾，不变。

完整性检验。 十一条规则都在吗，每条都附有它避免的故障？有没有哪条提案在放行重构或重写？

交付物。 带日期和版本的 docs/WORKING_AGREEMENT.md。

常见错误。 因为"逐步清理"听起来合理就接受它。它听起来合理，而它正是代理给自己授权去改没被要求的东西的方式。

在引导项目中。 代理提出两条自己的规则，值得接受："在这个系统里，任何真实发送都不会从测试环境出去：测试环境里的提醒发到一个假收件箱"，以及"负责人每个月下载的那张表格是系统的一个消费者，算作一份契约"。第二条是生产者-消费者地图提前冒头了，这没问题。

第 N2 课 — 阅读系统：恢复出来的地图和那些不一致

你需要理解什么。 这是整门课里每小时价值最高的一课。在第 2 课里，项目文件和树是从调研里出来的；在这里它们从系统本身出来，而且每条断言都带一个"它从哪里来"的标记：[代码]、[数据库]、 [配置]、[文档]、[业务] 或 [推断]。这些标记正是让你不读代码也能验证的东西：你去看那些推断出来的，确认它或纠正它。还会出现一份新文档，不一致清单：代码做的事、数据库强制的事和业务以为的事之间一切对不上的地方。它们不会自己解决：每一条都是你带日期做的一个决定。遗留系统永远有不一致；如果清单出来是空的，那是代理没有比对。

发送提示词之前，用你自己的手，和所有者一起：

  • 给代理读一切的访问权：整个仓库、数据库结构（只读，凭证放在聊天之外）、把密钥值遮住的服务器配置、最近的日志，以及现有的任何文档（在 Turnos 里，是侄子写的一封讲"怎么上传改动"的邮件）。
  • 在 docs/INITIAL_SURVEY.md 里，加一个和负责人一起写的新小节：她以为系统做了什么，一个用例一个用例地写，以及她记得的规则（"一个预约在不到两小时前不能取消"、"提醒是晚上八点发出去的"）。不要去对着系统核实：那个比对是代理的工作。
  • 住在仓库之外的东西的清单：提醒的那个定时任务，和那张连数据库的月度表格。
  • docs/WORKING_AGREEMENT.md 已关闭。
  1. 粘贴这条提示词：

We are going to recover the map of this system from what exists. Read the whole repository (every branch), the database schema (read-only), the configuration of each environment, the recent logs and whatever documentation there is; if some part cannot be read from where you are, tell me and mark it as a gap; do not fill it by guessing. Then write three things. First, complete docs/INITIAL_SURVEY.md in the form the method expects (what the system does and for whom; what it does NOT do; who uses it; the technology; the environments; what an error costs), with every statement tagged by its source: [code], [database], [configuration], [documentation], [business] for what the survey already says, or [inferred]. Second, PROJECT.md, three hundred lines at most, and docs/SEMANTIC_TREE.md: the domains and, under each one, the actors, the processes (each with trigger, steps, outcome and exceptions as the code actually implements them), the entities with the attributes, states and transitions the database and the code enforce, the screens, the external integrations and the scheduled jobs; every node tagged the same way. Third, docs/DISCREPANCIES.md: everything where the code, the database, the documentation and what the business says in the survey do not agree, with the evidence on each side. Do not resolve any discrepancy and do not fix anything: list them. Create docs/STATUS.md for the living state. Reply in my language.

我们要从现有的东西里把这个系统的地图恢复出来。读整个仓库（所有分支）、数据库结构（只读）、每个环境的配置、最近的日志，以及现有的任何文档；如果某部分从你所在的位置读不到，告诉我并把它标为缺口；不要靠猜来填它。然后写三样东西。第一，按方法预期的形式补全 docs/INITIAL_SURVEY.md （系统做什么、给谁用；它不做什么；谁在用；技术；环境；一个错误的代价），每条断言都带上来源标记：[代码]、[数据库]、[配置]、[文档]、对调研里已经写了的东西用 [业务]，或者 [ 推断]。第二，PROJECT.md，最多三百行，以及 docs/SEMANTIC_TREE.md：各个领域，以及每个领域下面的参与者、流程（每个带触发条件、步骤、结果和异常，按代码实际实现的样子写）、实体连同数据库和代码真正强制的属性、状态和状态转移、界面、外部集成和定时任务；每个节点都用同样的方式打标记。第三，docs/DISCREPANCIES.md：代码、数据库、文档，以及业务在调研里说的话，这四者对不上的一切，附上各方的证据。不要解决任何一条不一致，也不要修任何东西：把它们列出来。创建 docs/STATUS.md 来记录活状态。用我的语言回复。

你在要求它读完一切并声明读不到什么，要带标记的调研和树，要流程按代码实际实现的样子写（不是本该是的样子），要包含定时任务，以及要那些不一致列出来而不解决。

  • 有后果动作的调研（N5），加上"收定金"那一行，因为那是一个作用于现实世界的新动作：构建之前先上锁，和第 14 课一样。
  • 表征测试套件是绿的。
  1. 用第 5 课的开启提示词打开这个功能块，针对定金这个请求，然后像负责人那样读规格。
  2. 在构建之前，先上锁：对"收定金"这个动作粘贴第 14 课的收尾提示词，先用演练模式。
  3. 用第 8 课的例行构建，一条待办项一条待办项地来，配对项放在同一个功能块里。
  4. 功能块收尾时：完整的端到端测试套件（表征的那些加上新的那些），用第 8 课的功能块收尾提示词，再加上你自己用系统的一会儿功夫。

完整性检验。 定金在收款存在之前就有带红色测试的锁吗？功能块之后表征测试还是绿的吗？那个模块的配对项都偿还了吗？有没有旧模块里的东西在没有待办项的情况下被"改进"了？

交付物。 定金在测试环境里以演练模式跑起来，带着它的规格、它的锁、它的测试和它的端到端测试；配对项已关闭。

常见错误。 为了让它合得上就"快点、照其余部分的做法"构建定金：新模块永远带着完整的方法出生。还有因为"那是一个支付链接，又不是我们收钱"就忘了上锁：那个链接会发给一个患者；那就是一个对外的动作。

在引导项目中。 定金走的是和提醒同一个通道，而这个通道现在有了队列（N6 的那个不对称决策自己还了本）。锁：前台的显式确认，加上由专业人员设定的金额；演练模式跑一周，记录"本会向谁要定金"。取消界面那条配对项（那个确认）在这个功能块里偿还，因为定金改变了取消时会发生什么。收尾时，测试套件跑七个流程：五个表征流程、R1 那个 bug 的流程，和定金的流程。

之后：上线生产与运维

从这里开始，这个遗留系统就是一个有方法的系统了，第一部分的第 11 到 21 课原样适用，加四条注记。第一条是关于那六级运维质量台阶的：最低限度的可观测性和漏洞扫描已经随安全带进来了，持久化的测量已经在 N6 里，而负载测试用那些量级在第一次部署之前跑；两个监控以第一次阅读作为基线起步，而第一天就已经不对的东西带着它的标记变成待办项。另外三条注记是这些。第 13 课的审计要和 N3 那次对照：偿还了多少债务，还剩多少。第 20 课的手册在遗留系统里往往不存在，要根据系统的现状和那些已关闭的待办项生成，而那些待办项现在确实记录了做过的事。还有第 23 课的复盘多了一个这条路专属的问题：规范化花了多少成本（多少小时、多少 token、第一个改动之前多少周），以及标着"可以等待"的债务里有哪些最后还是照样付了代价。那个答案会在下一版里修正这一部分的日历。

规范化阶段的出口清单

所有者不读代码就能验证的八个条件，在打开第一个功能块之前。它们和演进-纠正之路那一页上的一样；我在这里重复一遍，因为它们是这一部分的交付物。

  1. 前面各个阶段的全部输入物都存在（调研、适格性、契约、项目文件、树、环境、容量、容量估算、闸门），带来源标记，而且所有者确认了每一个推断出来的节点（N2）。
  2. 每条不一致都有带日期的决定，要改系统的那些都有待办项（N2）。
  3. 审计存在，而且每条发现都有速度标记（N3）。
  4. 安全带是绿的：带匿名化数据的测试环境、部署跑了两遍、密钥在外面并且轮换过、持续集成、带演示过的变异红的表征测试套件（N4）。
  5. 每个有后果的动作都有裁决，而且"现在"的锁都有它们的红色测试（N5）。
  6. 原始数字都用带测试的量具测过，而且"乘以十"写下来了（N6）。
  7. 没有任何"阻塞"还开着，而且每条客户待办项都有它的配对项（N7）。
  8. 契约里有遗留系统的那五条规则，而且一个新会话能通过阅读测试（N1、N2）。
