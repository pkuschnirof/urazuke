1. 今天缺什么，以及为什么

台阶 9 已经在测量代码，而且是用一道不放行的闸门在测：单一格式化器、尺寸上限（每个文件三百行、每个函数四十行）、每个函数的复杂度、重复代码、死代码、已声明且被使用的依赖、带棘轮的覆盖率，以及在存在真实用户之处做变异测试。这个数字会写进 docs/CODE_QUALITY.md。那一半已经解决。

没有解决的是产品的另一半。我核对了台阶语料：其中没有一处提到可用性，也没有一处提到人／角色或功能分组。今天界面靠两样东西支撑：所有者看上十秒的截图，以及手工测试用例。两者都很好，但两者都靠人、都昂贵、都会遗忘。一个系统可以带着荣誉通过质量闸门，却完全不可用：一片全绿，而人找不到在哪里收款。

还有一层第二层的问题，它确实是技术问题，但在界面上看得出来：当同一个产品被多个角色使用（管理、运营、查询、客户）时，功能在三处不同的地方被启用——数据库、菜单和路由守卫——而这三处写在不同的时刻，并且会自己走偏。症状总是同一个：有人看到一个不属于他的按钮，或者更糟，一个明明有权限的人找不到那个页面。

下面这两套启发式规则用同一种形态对付这两件事：一份简短的可验证陈述目录、少数几个自行测量的工具，以及一条为项目需要越界时准备的、被声明出来的例外通道。

2. 模型：三层，规则只有一种形态

诱惑是列一份规则清单，然后把它绑到第一个项目的技术栈上。那种做法老得很快：React 的规则不适用于 Angular，Angular 的规则不适用于带模板的服务端，两年之后清单有一半是死的。这个提案把三层分开。

第 1 层 — 与技术栈无关的内核（不可谈判）。 陈述的是结果，不是工具。“只有一个格式化器，而且没有人跟它争”在 TypeScript、PHP 或 Go 里同样成立。内核用稳定的标识符逐条枚举，不随项目而变。

第 2 层 — 按技术栈的适配器（可配置）。 对内核的每条规则，每个前端家族声明*用什么*测量、*用哪个阈值*。一个用 Vite 的 React 项目、一个 Next 项目、一个 Angular 项目、一个带模板的服务端、一个移动端和一个命令行，是同一个内核的六个不同适配器。用户所要求的“按前端可配置”，全部住在这里。

第 3 层 — 项目的决定（声明出来的）。 具体阈值与豁免。它们不是凭空编的：向所有者索取，并写下来，就像架构台阶的规模测算一样。如果某个阈值没有被声明，就运行适配器的那个，并如实登记为该状态。

每条规则永远用同一张六字段记录来写：

字段内容
id稳定标识符（CQ-07、UX-12）。永不重用。
陈述一句关于可观察结果的祈使句。
为什么它避免的具体伤害。如果没有伤害，这条规则就是多余的。
如何验证工具：自动闸门、查询矩阵、端到端测试或人工用例。
严重级别BLOQUEA（阻断：闸门给红，块不关闭）、AVISA（警告：开一个待办项）、REGISTRA（记录：只留在文档里）。
适用范围生效的角色。不在其中就不运行，而这不是例外：是范围。

例外必须被声明，绝不省略。 一条规则被关掉，要有一份四字段记录：标识符、一行理由、谁批准（所有者，不是代理）以及复查日期。一条被关掉却没有记录的规则，是闸门的故障，不是一项决定。这和方法已经在用的判据一样：不接受为了“通过”而被抬高的上限。

3. 四个工具

任何启发式规则，如果它的验证是一种意见，就没有用。工具是四个，每条规则要声明自己属于哪一个。

  1. 自动闸门。 每次 push 和每个块关闭时运行。返回绿或红。它便宜、可重复，而且不争辩。凡是能数的东西它都测。
  2. 查询矩阵。 按角色的功能矩阵（见 B2）是一个声明式产物；菜单、路由和权限都由它派生。检查矩阵就是检查界面。这就是把一部分可用性变成机器可验证的那个零件。
  3. 按角色的端到端测试。 对每个声明的角色，一个以该角色进入的脚本，把可到达的功能集合与矩阵中那一行做比较：*不多不少*。这是抓住两种典型走偏的测试（多出来的按钮和缺失的页面）。
  4. 人工用例。 机器无法判断的东西：分组是否讲得通、任务能否不求人地完成、文本是否在用户的语言里。它由人来执行并被记录，正如台阶 10 已经要求的那样。

4. A 部分 — 代码质量

内核延展台阶 9：它不替换、也不与它矛盾，而是给每一件已经在测的事加上名字、严重级别和适配器，并补上今天缺的东西，也就是被当作代码来看的界面。

CQ-12 到 CQ-18 这些规则，正是让“代码质量”在前端有意义的东西。没有它们，项目可以拥有百分之九十的变异得分，却有一个组件用自己的算术在算总价：两个世界中最坏的那一个，因为重复的计算通过了后端的全部测试。

初始严重级别（D-048）。 从第一天起就阻断的，是十四条有验证器、且不依赖需要讨论的阈值的规则：CQ-01 至 CQ-06、CQ-08 以及 CQ-11 至 CQ-17。CQ-09 在有真实用户之处阻断，因为那才是被测量之处。警告的有三条，而且只有三条：CQ-07（类型）、CQ-10（依赖）和 CQ-18（无障碍），因为它们需要项目先做校准。格式化器、linter、尺寸和复杂度不放宽：台阶 9 今天就已经阻断它们，这里是延展它，不是替换它；遗留债务用一条声明出来的例外、或用棘轮的基线来解决，绝不靠降低规则的严重级别。而 CQ-12 和 CQ-14 是本表中仅有的两条以人工红、而不是机器红来阻断的规则：它们在待办项关闭时验证，把人工用例摆在面前，判据与 UX-22 和 UX-27 相同，而不是在每次提交时。如果项目撑不住这种关闭，规则降为 AVISA，那是因为有登记的决定，不是因为遗忘。

5. B 部分 — 可用性

六个家族。第一个和第二个是所有者明确要求的；另外三个之所以存在，是因为没有它们，分组和角色会以同样的方式退化，只是更慢。 第六个是后来才有的，在 2026-10-27（D-070），性质也不同：前五个讲系统给人看的页面，第六个讲系统被建造时的那场对话。

B1 — 按功能收敛的分组

母规则：一个功能按人来做的事分组，而不是按它出自哪个模块分组。 代码按实体组织（“发票”“客户”“付款”）；人不这样。没有人是为了“管理实体”进入系统的：人是为了收款、发货、结账而进来。如果菜单显示的是实体，人就得当翻译。菜单*就是*工作。

id陈述验证严重级别
UX-01菜单的每个分组都用一个用户的工作来命名（用他的词汇，用项目的术语表），绝不用技术模块或数据实体命名。人工用例 + 矩阵审查警告
UX-02每个功能恰好有一个归口。如果它服务两个分组，就选一个归口，从另一个链接过去；入口不复制。查询矩阵阻断
UX-03没有孤儿：每个声明的功能都能从入口页面在三步之内到达。沿路由的自动遍历阻断
UX-04分组的大小是合理的：少于三个功能说明它本来不是分组；多于七个说明它是个抽屉。查询矩阵警告
UX-05每个分组都有一个入口页面，说明在这里做什么、主操作是什么。没有哪个分组一打开就是一张空表。人工用例警告
UX-06人经常做、连在一起做的流程住在一起：如果“录入一笔付款”和“查看该客户的账户”在同一次会话里被使用，它们共用一个分组。人工用例（任务测试）记录

B2 — 角色与按角色启用的功能

这里是最出产的那个零件，而理由是工程上的，不是设计上的：启用只在矩阵里声明一次，其余的一切都从它派生。 今天经典错误是把权限写三遍（菜单里、路由守卫里和数据过滤里），然后三者分开。以矩阵为唯一生产者，菜单、路由、服务端权限和测试脚本都是消费者，而方法已经要求的生产者／消费者对称就自己变得可验证了。

矩阵有四列，每个功能一行：*功能*、*归口*（B1 的分组）、*拥有它的角色*、*进入路由*。仅此而已。

UX-08每个功能都在矩阵里声明哪些角色拥有它。没有角色的功能不存在：要么给它分配角色，要么删掉。查询矩阵阻断
UX-09每个声明的角色至少有一个功能和自己的入口点。空角色是设计时没人用过的角色。查询矩阵阻断
UX-10导航由矩阵生成。手写的菜单是故障，不是捷径。闸门（检索）阻断

UX-13拒绝要说清：如果一个人进入不属于他的功能，他看到一个消息，说明为什么、该向谁申请权限。绝不是空白页面，绝不是没有理由的灰按钮。人工用例警告

UX-15数据也按角色过滤：看到列表的人看到属于他的那些行，而不是在浏览器里把行藏起来的完整列表。端到端测试 + 服务端审查阻断
UX-16矩阵和用户手册在与功能同一个待办项里更新。没有矩阵行的新功能不关闭。待办项关闭阻断

B3 — 状态，以及当某样东西不在时人看到什么

大多数“不能用”的投诉，是不会说出“什么都没有”“正在加载”或“失败了”的页面。四个状态，永远，在每张列表和每个详情页面上。

B6 — 向所有者提问

方法在一半以上的提示词里命令模型提问：二十二次，分布在已发布语料的二十七个文件中的十五个。可是直到 2026-10-27，它在任何地方都没有说过该怎么问，于是形式交给了临场发挥，所有者收到的是一个光秃秃的问题：没有让它成为必要的数据，没有选项，也没有推荐。这正是第 11 级台阶追的那种不对称——一边要求，另一边不定义——而且是在代价最高的方向上：朝着做决定的那个人。方法已经做过两次这件事：第 8 级台阶不满足于"把红给我看"，定义了什么是收据；第 12 级台阶不满足于"报告"，把已验证和相信分开了。

三个深度层级，以及它们从哪里来。 项目声明一个，代理就在那个层级说话：beginner（日常语言，面向结果，不出现文件名也不出现术语）、decision_maker（测出来的数字和后果，不出现文件路径：方法默认用的那个）和 technical（文件、行、命令）。它们不是为这条规则发明的：初学者层级本来就是整个方法的形式（D-025）。参数名和三个取值住在数据层，在 project_config.communication_depth 里，因为那是消费方工具必须读到、而不该去猜的东西。

这条规则不承诺什么。 闸门可以验证这段条款出现在七十二条提示词和八种语言里——它确实在做；但没有任何测试能验证某个星期二模型写下的那个具体问题是否带着它的四个部分。那由所有者来判断，这也是这条规则警告而不阻断的原因。一条阻断却没人能验证的规则，比一条警告的规则更糟：这跟 CQ-12 和 CQ-14 已有的那条声明出来的限制是同一条。

6. 它挂接在哪里，产生哪些产物

本附录不发明新的台阶：它挂在已经存在的台阶上。这避免了闸门重复，也避免了可用性清单通常的命运——被读一次。

它放在哪里（D-043）。 它横贯四个阶段，主要重量在建设循环（台阶 5 到 12），因为那才是做决定和施工的地方。它不是自己的一个台阶：一个编号台阶会迫使整条梯子重编号、改变步数计数，并让本附录在建设转绿之前就受制于合同必须译成八种语言的义务，却不增加任何循环本来没有的闸门。

它如何挂接（D-044）。 一份唯一来源、五个锚点和两个前置入口。规则文本只住在这里，提示词引用它；绝不复制它。把四十五条规则重复进循环的八条提示词里，会稀释它们（它们与每个台阶自己的工作竞争，代理每次遵守得都不一样）、使它们走偏（同一文本的两份副本会自己不同步，正是台阶 11 所追的那种反模式），也不会让它们更横向：让一条规则横向的，是每个块都经过同一道闸门，而不是规则被写在所有地方。

唯一进入提示词的规则，以及为什么（D-070）。 UX-28 是对上面那条原则写下来的例外，值得说清它跟另外四十五条的区别：那些是对被建造的系统的要求，闸门在项目留下的产出物上测量它们；UX-28 是对建造时那场对话的要求，而让模型遵守它的唯一办法，就是它出现在模型读到的东西里。它进得很窄——只点出四个部分和那个参数，别的不说——以一段在八种语言里完全相同的英文写法。这个例外不授权去抄别的任何一条：对于闸门能看的一切，D-044 的论证整条仍然成立。

8. 这两件东西，按方法使用的形态

代码质量。

Set up and maintain the code-quality gate for this project, configured for its frontend family. The core rules are the same in every project; what changes is how each one is measured and at which threshold. Install one formatter and one linter with a single shared configuration; enforce size limits per file and per function, complexity per function, duplication, dead code, declared-and-used dependencies, type checking where the language allows it, coverage with a ratchet, and secret scanning. Where the project has real users, add mutation testing scoped to the changed lines and record the score per block. Then extend the gate to the frontend itself: no business rule inside a screen, one typed client for every server call, one home for shared state, no user-visible string outside the translation catalogue, a stable identifier and role on every interactive element, styling only through tokens, and automatic basic accessibility checks. Every rule has a stable id, a severity (blocks, warns, records) and a named verifier. Thresholds and exceptions are declared by the owner in one configuration file; a rule switched off without a written exception is a gate failure, not a decision. Report the result per rule in docs/CODE_QUALITY.md, not as a single number.

When you need a decision from me, ask it with the four parts of UX-28 (docs/ANEXO_HEURISTICAS.md) and in this order: the data that makes the question necessary, listed; one paragraph of at most five lines that links that data and lets the question be seen; the question itself with its possible answers numbered; and your recommendation. Say it at the technical depth the project declared in communication_depth -- beginner, decision_maker or technical; if the project declared none, use decision_maker.

为本项目搭建并维护代码质量闸门，按它的前端家族来配置。内核规则在每个项目里都一样；变的是每条规则用什么测量、在哪个阈值上测量。安装一个格式化器和一个 linter，共用一份配置；强制每文件和每函数的尺寸上限、每函数的复杂度、重复、死代码、已声明且被使用的依赖、语言允许时的类型检查、带棘轮的覆盖率以及密钥扫描。在项目有真实用户之处，增加限定在改动行上的变异测试，并按块记录得分。然后把闸门延展到前端本身：页面里不放业务规则、每次服务端调用只有一个带类型的客户端、共享状态只有一处存放地、翻译目录之外不出现任何用户可见字符串、每个可交互元素都有稳定标识符和角色、样式只通过设计令牌、以及基本的无障碍自动检查。每条规则都有稳定编号、严重级别（阻断、警告、记录）和有名字的验证器。阈值和例外由所有者在同一个配置文件里声明；一条被关掉却没有书面例外的规则属于闸门的故障，不是一项决定。在 docs/CODE_QUALITY.md 里按规则报告结果，不要汇成一个数字。

可用性。

Build the usability criteria for this project before writing the first screen, and enforce them where the method already has hooks. Group functionality by what the person came to do, never by the internal module or the data entity: every menu group is named with a user job in the project glossary, every functionality has exactly one canonical home, no functionality is orphaned, and every group is reachable in no more than three steps from the entry screen. Then declare accessibility in one matrix and derive everything from it: each functionality lists the profiles that have it, each functionality has at least one profile, each profile has at least one functionality and its own entry point, the navigation is generated from the matrix instead of written by hand, and every route checks the permission on the server because hiding an entry is not protecting it. Verify the matrix per profile with an end-to-end check that compares what is reachable with the matrix row: neither less nor more. Require the four states on every list (with data, empty, loading, error), a visible working indicator with the option to cancel long operations, an error message that says what happened and what to do without losing entered data, a primary action per screen, confirmation or undo for destructive actions, and a form that keeps what was typed. Run each manual test case once per affected profile, run the first-click check at the close of every block, and require a real screenshot of the test environment on every item that touches a screen. Record the result per rule, with owner-declared exceptions, in docs/USABILITY.md, and keep the matrix in docs/PROFILE_MATRIX.md as the single source of truth.

When you need a decision from me, ask it with the four parts of UX-28 (docs/ANEXO_HEURISTICAS.md) and in this order: the data that makes the question necessary, listed; one paragraph of at most five lines that links that data and lets the question be seen; the question itself with its possible answers numbered; and your recommendation. Say it at the technical depth the project declared in communication_depth -- beginner, decision_maker or technical; if the project declared none, use decision_maker.

在写第一个页面之前，为本项目建立可用性准则，并在方法已经有挂接点的地方强制它们。按人来做的事分组功能，绝不按内部模块或数据实体分组：菜单的每个分组都用项目术语表里的一个用户工作来命名，每个功能恰好有一个归口，没有任何功能成为孤儿，每个分组都能从入口页面在三步之内到达。然后用一个矩阵声明无障碍，并从中派生一切：每个功能列出拥有它的角色，每个功能至少有一个角色，每个角色至少有一个功能和自己的入口点，导航由矩阵生成而不是手写，每条路由都在服务端校验权限，因为把入口藏起来保护不了任何东西。按角色用端到端测试验证矩阵，把可到达的内容与矩阵那一行比较：不多不少。要求每张列表都有四个状态（有数据、空、加载中、出错）、一个可见的进行中指示并能取消长操作、一条说明发生了什么和该做什么且不丢失已录入数据的错误消息、每个页面一个主操作、破坏性操作的确认或撤销，以及一个保留已输入内容的表单。每个手工测试用例对每个受影响角色跑一次，每个块关闭时跑首次点击测试，并要求每个触及页面的待办项都附上测试环境的真实截图。按规则记录结果，连同所有者声明的例外，写进 docs/USABILITY.md，并把矩阵保存在 docs/PROFILE_MATRIX.md 里作为唯一真相来源。

当你需要我做决定时，用 UX-28（docs/ANEXO_HEURISTICAS.md）的四个部分来问，并按这个顺序：让这个问题成为必要的数据，列举出来；不超过五行的一段话，把这些数据连起来并让问题显现；问题本身，可能的答案逐一编号；以及你的推荐。用项目在 communication_depth 中声明的技术深度来说——beginner、de cision_maker 或 technical——；项目没有声明就用 decision_maker。

9. 这个提案不做什么

  • 它不增加台阶。 是四十六条横向规则（18 条质量、28 条可用性），不是一个新阶段。它们挂在已经存在的台阶上。
  • 它不发明一个分数。 一个“可用性 78”的数字不说明该修什么，而且会被往错的方向优化。按规则报告。第 12 节提出两个派生数字，但它们是带依据的规则计数——不是质量或可用性的评分——也不授权关闭任何东西。
  • 它不取代所有者。 首次点击测试、截图和任务测试仍然是人的：它们是唯一能区分“能运行”和“有用”的工具。
  • 它不带来出厂阈值。 适配器的那些是一个声明出来的起点；不声明自己阈值的项目继承它们，并被登记为该状态。
  • 它不承诺闸门能发现糟糕的分组。 机器可以验证没有重复、没有孤儿；如果一个分组叫“管理”，那得由人来看。

  1. 计数的缺陷。 凡是本附录说“二十七条规则”的地方，正确的数字是四十五条：18 条质量（CQ-01 至 CQ-18）和 27 条可用性（UX-01 至 UX-27）。那个旧数字来自一份只数了一半的草稿。已在第 6 节和第 9 节更正，并在 D-048 中记下；D-044 的文本按原样保留，因为一项决定是一份登记，不重写。
  2. 格式化器、linter、尺寸和复杂度不放宽。 这份建议的一个早期版本把它们送去“警告”，为了不阻塞带遗留债务的项目。这不可能：台阶 9 今天就已经阻断它们，而这次延展是延展，不是替换。遗留债务用一条声明出来的例外——带理由和复查日期——或者用棘轮的基线来解决，不是靠降低规则的严重级别。

而从 2026-10-27 起是四十六条。 UX-28 随 D-070 进来，数目变成 18 条质量和 28 条可用性。上面那条注记保持原样，因为一次更正也是一份记录；一条新规则改变的是数目，不是数目的历史。

还有一条声明出来的限制，因为它是同类中唯一的一条：CQ-12 和 CQ-14 以人工红来阻断。 没有任何工具能证明一个页面不做业务决定。它们在待办项关闭时验证，把人工用例摆在面前，判据与 UX-22 和 UX-27 相同；如果项目撑不住这种关闭，它们因登记的决定降为 AVISA。一条阻断却没人验证的规则，比一条警告的规则更糟。

日历上的待办，不是决定上的待办

11. 如何验证闸门确实在把关

一条启发式规则，如果开关它不改变任何东西，那就不是闸门，是装饰。实现的验收测试（PND-002）是一个夹具项目，里面故意种下每个家族的违规：

场景要求的结果
质量开启，带违规红，并指出规则和违规所在的文件。
质量关掉有登记绿，且报告说明它被关掉、从何时起、谁批准的。
质量关掉没有登记红。没有书面理由就关掉是故障，不是规则的缺席。
可用性开启，有角色越界到达UX-12 变红，并指出角色和功能。
可用性开启，有功能在矩阵里没有行关闭待办项时 UX-08 变红（UX-16）。
两组都关掉两边都绿，报告里有两行关掉说明。
种下一条警告规则的违规绿，并开一个待办项，指出规则和文件：警告不等于批准。
种下一条阻断规则的违规红，并指出规则、文件和补救办法。而且没有看板：平均值不关闭块。

看板：两次运行，规则集不同两个数字都带着各自的指纹（目录版本、启用与关掉的规则、适配器、工具版本）显示，并且不画成一条连续序列：它们是两把不同的尺子，说出这一点是结果的一部分。
看板：规则集无效（规则被关掉却无登记）不输出数字。输出是红，不是一个带星号的看板。

要看的不仅是颜色：要看报告里那两行关掉说明是否存在。一个没有这一行的绿色结果，是这项测试唯一无法仅凭颜色发现的故障，所以它靠读输出来验证。

12. 合规看板（已决定：两个数字，D-047）

状态。 2026-10-22 在 D-047 中决定：看板带两个数字、带规则集指纹、带棘轮、把人做的部分排除在百分比之外，并且依据是强制的。它不授权关闭块。以下是实现（PND-002）必须满足的规格。

它是什么。 它是闸门已经输出的按规则结果的一个确定性派生。它不测任何新东西，也不判断任何新东西：它数数。如果看板能改变一条规则的裁决，同一件事就有了两个真相来源，而那正是本附录在 UX-10（导航由矩阵派生）和 CQ-14（状态只有一处存放地）里所对抗的。

它不是什么。 它不是验收标准。没有任何数字授权关闭一个块：绿还是红，由每条阻断的规则逐条决定。看板描述趋势、指出该看什么。如果它开始被当作关闭阈值来用，它就不再有用，因为把数字抬上去最短的路是关掉规则。

两个数字，永远不是一个。

数字公式测量什么如何变动
合规率通过的规则 ÷ 启用的规则正在被看的那部分有多干净修好时上升
闸门覆盖率启用的规则 ÷ 目录中声明的规则本附录有多少真的在看关掉一条规则时下降

为什么是两个：关掉一条规则会抬高合规率，并降低覆盖率。只有一个数字时，关掉是免费的，看板奖励的是失明。有两个朝相反方向移动的数字，这条捷径就消失了：要展示更好的看板，得去修代码，而不是关规则。而覆盖率不测量就无法提高。

规则集的指纹。 每条记录都保存它用什么尺子算出来：目录版本、启用与关掉的规则、前端适配器以及工具版本。没有这些，昨天的 82 和今天的 91 尽管写得一样，却不是同一种测量：它们是两套不同的规则集，序列是假的。两个没有指纹的数字制造进步的幻觉，那比没有看板更糟。如果指纹变了，记录被标为不可比较，或者历史按现行尺子重算；绝不不加说明地画在一起。

棘轮。 合规率不会从一个块到下一个块自行下降，除非有一条解释它的登记决定。这与 CQ-08 中测试覆盖率已经拥有的机制相同：今天的数字是明天的底线。下降不被禁止；没有登记就下降，被禁止。

不进账的东西。 只有人才能判断的东西——首次点击测试（UX-07）、任务测试（UX-06）、截图（UX-27）以及所有人工用例——按块登记为通过或失败，带名字和日期，并作为人类验证覆盖率单独报告。它不进合规率百分比。如果混在一起，结果就是一个百分之六十测量、百分之四十意见的数字，而没人能说出哪一部分是哪一部分。所以第 9 节仍然有效：看板不发明可用性评分，它数规则。

如何证伪它。 扩充第 11 节的验收测试：

场景要求的结果
种下一条阻断规则的违规合规率恰好下降一条规则除以启用规则数，并出现指出规则的红色。
一条规则带登记被关掉合规率可以上升；覆盖率下降一条规则除以声明规则数；报告指出规则、理由和复查日期。
没有登记就关掉红，并且不输出看板：无效的规则集不产生数字。
同一棵树、同一份配置，跑两次同一个数字，完全相同。
两个块之间配置改变两条记录都被标为不可比较，或者历史按现行尺子重算。
看板被用作关闭标准不当使用，不是有效场景：绿由规则决定，不是由平均值决定。

它出现在哪里。 在台阶 12 的诚实报告里（锚点 5），并且按这个顺序：先是闸门的二元裁决，然后是两个数字，然后是什么被关掉、关到什么时候，最后是相对上一个块的变动及其被命名的原因。永远带着依据：*下降了四分：CQ-15，收款页面上有三条字符串在目录之外*。没有依据的数字是噪音；依据才让它对一个不读代码的所有者变得可执行。

已声明的风险。 看板会被所有者读，而他不读代码，所以他会希望它上升。数字变成目标，而目标会挤掉目的。防线就是上面那五条，而且正好五条：关掉时相互矛盾的两个数字、让不同尺子无法比较的指纹、不允许无登记下降的棘轮、把人做的部分排除在百分比之外，以及强制的依据，加上绝不用平均值谈判的闸门。这五条里任何一条倒了，看板就关掉：一个被误用的看板，比没有看板害处更大。
