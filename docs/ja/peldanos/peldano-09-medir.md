# ステップ 9 — 構築の前に計測する、自身も検証される計器で（段の契約）

**区間：** ループ。
**いつ：** 保留項目が数字または原因の仮説に依存するたびに、構築の**前**に。立ち上げでは
サイジングが最初の事例。小さいプロジェクトでは「計測する」とはコマンドで数えて数字を日付
とともに記すことだ。
**形式：** 計測ごとに一回の送信。仮説があなたのものなら、ときに対話。
**規模：** 比例的。ラチェットとクエリ予算はボリュームのあるシステム向け。規模で変わらない
もの：何かを決める数字は印象からは出ない。

## 何のためか

決定に入力されるすべての数字が、テキスト検索でも、印象でも、「百くらいだと思う」でもなく、
テスト付きのプログラムから出るようにすること。そして計器自体を監査させること。計器は嘘を
つくからだ。私のものの一つはカウンタゼロのまま84回の呼び出しを見ておらず、別のものは44
なのに27と言っていた [Ref. 35](../REFERENCIAS.md#ref-35)、
[Ref. 36](../REFERENCIAS.md#ref-36)。その後私が書いた五つのルール：ガード付きの計器。計器が
なければ作る。双方向で監査する。近似は印す。そして実行者は計画者の数字を検証する。

この段は私が形式化するのに最も時間がかかったもので、語る価値のある理由がある。「触る前に
計測しろ」というこれほど基本的な工学のことを、モデルは独りで適用するだろうと当然視して
いた。適用しない。モデルは数字付きの主張（「その種のループは120ほどある」）を作るのが非常に
うまく、その主張は計測されたときも推定されたときもまったく同じに聞こえる。口調で区別する
術はない。唯一の方法は計器を要求することだ：「何で計測した？ コマンドを見せて」。コマンドが
なければ、小数点がいくつあろうと印象だ。これらのルールは、教義になる前に、セッション中に
エージェントを訂正しながら私が課したものだ [Ref. 45](../REFERENCIAS.md#ref-45)。

## 1. 必要な文脈

- 仮説、あなたのものかエージェントのもの：「問題はXだと思う」「百くらいのはず」。
- 計測したいものへのアクセス：コード、読み取り専用のデータベース、ログ。
- リポジトリに既にある計器、あれば。

## 2. プロンプト

**最初：**

> Before building anything, we are going to measure. The hypothesis is: [X]. Write a meter (a
> script that lives in the repository) that measures [the quantity], and a test for the meter
> that checks it against a known case where the answer is known in advance. If measuring
> requires access or data you lack, ask me; do not approximate silently. If some part can only
> be approximated, mark it as approximate and tell me the margin. Run the meter, show me the
> number together with the command that produces it, and audit it in both directions: from the
> code to the measurement (is everything that should be counted, counted?) and from the
> measurement to the code (does everything counted actually exist?). Only then propose what to
> build. Reply in my language.

> [ja]
> 何かを構築する前に計測します。仮説は：[X]。[量]を計測する計器（リポジトリに住むスクリ
> プト）と、答えが前もってわかっている既知の事例に対してそれを検証する計器のテストを書いて
> ください。計測にあなたが持っていないアクセスやデータが必要なら、私に求めてください。黙って
> 近似しないでください。ある部分が近似しかできないなら、近似と印して誤差の幅を教えてくだ
> さい。計器を実行し、それを生むコマンドとともに数字を見せ、双方向で監査してください：コード
> から計測へ（数えるべきものはすべて数えられているか？）、計測からコードへ（数えられたもの
> はすべて実際に存在するか？）。その後初めて何を構築するか提案してください。私の言語で答えて
> ください。

何を求めているか、条項ごとに：**リポジトリ内**の計器（失われる単発のコマンドではなく）。
既知の事例に対する**計器のテスト**（ガード）。計測に合わせた形の完全性の条項（アクセスを
求める、黙って近似しない）。近似を誤差の幅付きで印す。それを生む**コマンド付き**の数字、
あなたが実行できるように。双方向の監査、私の嘘をついた二つの計器の正体を暴いたもの。
そして順序：まず計測、次に提案。

**予算があるとき：**

> Set the budget for [queries / loops / time] on this path at the measured value plus a small
> margin, and protect it with a test that fails if it is exceeded. Tell me the number and the
> margin.

> [ja]
> この経路の[クエリ / ループ / 時間]の予算を、計測値プラス小さな余裕に設定し、超えたら
> 失敗するテストで守ってください。数字と余裕を教えてください。

何を求めているか：予算が丸い数字ではなく計測値プラス少しであること、そして超えたら失敗
するテストがあること。こうして性能の退行は本番ではなくテスト群で現れる
[Ref. 37](../REFERENCIAS.md#ref-37)。

**計画者が数字を出したとき（ルール五）：**

> Before executing the plan, verify every number the plan asserts with the meter. If any does
> not match, stop and tell me; do not execute on a wrong number.

> [ja]
> 計画を実行する前に、計画が主張するすべての数字を計器で検証してください。一致しないものが
> あれば、止まって私に教えてください。間違った数字の上で実行しないでください。

何を求めているか：実行者が計画者の数字を信用しないこと、別のセッションの同じモデルでも。
私の場合、計画の四つの主張のうち三つが間違っていた。計器があったところでは、数字は正確
だった。

## 3. 期待される成果物

- リポジトリ内の計器（`tools/measure_*.py`、`scripts/meter-*.mjs` など）、そのテスト付き。
- 数字、それを生むコマンドと日付付き。
- 双方向の監査、二、三行で書かれて。
- 近似はそうと印され、誤差の幅付き。
- 予算があるなら：値、余裕、それを守るテスト。
- コミットに："measured: [number] with [meter]"。

## 4. 完全性の検証

- あなたが計器のコマンドを実行して同じ数字が出るか？（あなたが実行する。理解する必要は
  ない。実行するだけでよい。）
- 計器にテストはあるか？ どの既知の事例に対して？
- 報告に計器の裏付けのない数字があるか？ どこから出たか聞くこと。
- 近似は印されているか？
- 計画が数字を持っていたなら、エージェントは実行前にそれを検証し、どれが合わなかったか
  あなたに言ったか？

## 5. 警告サイン

- コードが変わっていないのに二つの報告の間で数字が変わった。どちらかは計測されていない。
- 計器がゼロを出す。ほとんどの場合ゼロではない。ほとんどの場合計器が何かを見ていない。
- エージェントが時間を稼ぐために「計測しながら」構築することを提案する。順序が方法だ：
  まず数字、次に計画。
