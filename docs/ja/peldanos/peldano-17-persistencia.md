# ステップ 17 — 永続化層の最適化、前と後を計測して（段の契約）

**区間：** 本番リリース。
**いつ：** 本番リリースのフェーズで、第16段の後（クエリを計測するにはそれが見えなければなら
ない）、第19段の前に（性能テストは最適化済みの永続化の上で走る。さもなければ既にわかっていた
問題を計測することになる）。ブロックが大きいテーブルを追加したり重要なフローを変えたりしたと
き、そして監視（21）がクエリの範囲外を示したときに繰り返す。レガシーでは、計測はN6から出て、
見つかるもののほとんどは「触れたときに払う」で払われる。既に範囲外のものを除いて。
**形式：** 二回の送信：計測して提案する。前と後とともに適用する。
**規模：** 比例的：小さいプロジェクトでは実際のクエリのインデックスとN+1ループの終わり。帰結
のあるプロジェクトでは完全版、経路ごとの予算付きで。

## 何のためか

永続化層はシステムがゆっくり死ぬ場所だ：百件ではよく動き、一万件でもまあ動き、十万件になると
画面ごとに二十秒かかり、いつ始まったのか誰も知らない。この段は、それが苦情と事後ではなく、数
字と本番の前に決められるために存在する。そして**第7段の方法で**決められるために：システムが
行う各クエリをテストを持つ計器で数えて計時し、数字が言うことを変え、同じデータの上で計測し直
す。生きたシステム上のインデックスのないクエリの最初の監査 [Ref. 18](../REFERENCIAS.md#ref-18)
と、計測値に締められたクエリ予算 [Ref. 37](../REFERENCIAS.md#ref-37) がこの段の出所であり、一行
目からの非同期インターフェースの決定 [Ref. 15](../REFERENCIAS.md#ref-15) がその立ち上げにおける
先例だ。

何でないか：「データアクセスを書き直す」ことでも、別のエンジンを選ぶことでもない。それは第3
段が決めた。これは、実際のクエリがしていることから出発して、あるもの（インデックス、ページン
グ、バッチ、保持、プールの大きさ）を調整することだ。

**初心者の方へ。** *永続化層*とは、システムのうちデータを保存して読む部分のことで、ほとんど
の場合データベースです。*インデックス*は本の索引のようなものです：それがなければ、一つの予約
を見つけるためにデータベースはテーブル全体を読みます（それが*フルスキャン*です）。あればまっ
すぐ行きます。*N+1ループ*はとてもよくある誤りです：百件の予約を表示するために、システムは一
覧のために一回のクエリをし、その後さらに百回、予約ごとに一回クエリをします。一回で済むのに。
*ページング*とは、全部まとめてではなく二十件ずつ表示することです。*保持*とは、各データを保管
しておいてから書庫に入れるか削除するまでの期間です。そして*接続プール*とは、システムがデータ
ベースとの間に同時に持っている「開いた回線」の数です。これらのどれも、あなたがコードを読むこ
とを求めません。前と後の数字を見ることを求めます。

## 1. 必要な文脈

ここに続くのは一般的なリストです。各プロンプトの前にあなたが作り終えていなければならない具体
的なファイルは、その内容と最低限受け入れられる状態とともに、第2節の、それぞれのプロンプトに
先立つ「プロンプトを送る前に」の枠に書いてあります。

- サイジングとボリューム（第3段、またはレガシーではN6）：計測すべき量。
- 生産者・消費者の地図（第11段）：どのテーブルを誰が消費するか。
- 可観測性（16）：各クエリがその時間とともに見えること。
- 期待される量のデータを読み込んだテスト環境。

## 2. プロンプト

**最初（計測して提案する）：**

**プロンプトを送る前に**、次のものが存在していなければなりません。作るのはあなた（または業務
側とあなた）で、エージェントではありません：

- `docs/SIZING.md` と `docs/VOLUME_SURVEY.md`（第3段またはN6）、締められたもの：読み込むべき
  量。
- **期待される量の**データを持つテスト環境。十件のサンプルではなく。以前のシステムか本番があ
  れば匿名化したコピーを。新規プロジェクトなら、セマンティックツリーの形とサイジングの量で合
  成データを生成し、リポジトリにスクリプトとして残すようエージェントに求めてください。これは
  このプロンプトの一部ではなく、先行する保留項目です。
- `docs/PRODUCER_CONSUMER_MAP.md`（第11段）、最新のもの。
- 本番があるなら：読み取り専用のアクセス、認証情報はチャットの外に。テストのデータに加えて実
  データの上でも計測するためです。
- 各計器のテストのための既知の事例（行数をあなたが知っているテーブル一つ）。
- 最低限受け入れられる状態：テスト環境がサイジングの量を持ち、エージェントが各クエリをその時
  間とともに見られること（第16段）。

> We are going to optimize the persistence layer with measurements, not opinions. Read
> `docs/SIZING.md`, `docs/VOLUME_SURVEY.md` and `docs/PRODUCER_CONSUMER_MAP.md`. With the test
> environment loaded at the volumes of the sizing (and, if I gave you access, production
> read-only), measure first, with meters that live in the repository and have a test against a
> known case: every query the system runs per screen and per job, with its count and its time;
> the queries that read whole tables; the ones that run once per item; the size and monthly growth
> of every table; the connection pool usage at the peak. Audit each meter in both directions. Show
> me the numbers with the commands that produce them. Then propose, query by query, what to
> change: indexes derived from the real queries, pagination, batching, the elimination of N+1
> loops, retention and archiving per table, pool size; for each change, the expected gain, the
> risk, and which consumers in the map it touches. Do not change anything yet: I approve the list.
> Reply in my language.

> [ja]
> 意見ではなく計測で永続化層を最適化します。`docs/SIZING.md`、`docs/VOLUME_SURVEY.md`、
> `docs/PRODUCER_CONSUMER_MAP.md` を読んでください。サイジングの量を読み込んだテスト環境で
> （そして、私がアクセスを与えたなら、読み取り専用の本番で）、まず計測してください。リポジト
> リに住み、既知の事例に対するテストを持つ計器で：システムが画面ごと、ジョブごとに走らせるす
> べてのクエリを、その回数と時間とともに。テーブル全体を読むクエリ。項目ごとに一回走るもの。
> 各テーブルの大きさと月ごとの増加。ピークにおける接続プールの使用。各計器を双方向で監査して
> ください。数字を、それを生むコマンドとともに見せてください。その後、クエリごとに、何を変え
> るかを提案してください：実際のクエリから導かれるインデックス、ページング、バッチ処理、N+1
> ループの除去、テーブルごとの保持と書庫入れ、プールの大きさ。各変更について、期待される利
> 得、リスク、そして地図のどの消費者に触れるか。まだ何も変えないでください：リストは私が承認
> します。私の言語で答えてください。

何を求めているか：提案する前に第7段の方法で計測すること（テスト付きの計器、双方向で監査、コ
マンド付きの数字）。クエリごとに、利得とリスクとともに、そして各変更が触れる地図の消費者とと
もに提案すること（新しいインデックスは誰にも触れないが、テーブルごとの保持はそのテーブルを読
む全員に触れる）。そして**私が承認するまで何も変えない**こと。最適化は、誰も頼んでいないもの
を最も多く「改善」される場所だからだ。

**締め（前と後とともに適用する）：**

**プロンプトを送る前に**、次のものを手元に用意しておいてください：

- 提案された変更のリスト、あなたが読んだもの、一つずつのあなたの承認か却下付きで。却下したも
  のには一行の理由。地図の消費者に触れるものについては、彼らにとって何が変わるかをあなたが理
  解しているという確認。
- 計測の数字の一つ（例えば最大のテーブルの月あたりの行数）について、あなたが手でやり直した計
  算、一致するもの。
- 最低限受け入れられる状態：各変更に判定があり、どの消費者に触れるかを理解していること。

> Apply the approved changes [list], one commit each. For each one show me the meter before and
> after on the same data, the regression suite green, and the end-to-end suite green. Set a budget
> per critical path (queries and time) at the measured value plus a small margin, protected by a
> test that fails if it is exceeded. Update every consumer in the map that a change touches, in
> the same commit. Record the before and after table, the budgets and the retention per table in
> `docs/PERSISTENCE.md`.

> [ja]
> 承認された変更[リスト]を、一つにつき一コミットで適用してください。それぞれについて、同じ
> データの上での前と後の計器、緑の回帰、緑のエンドツーエンドのテスト群を見せてください。重要
> な経路ごとに予算（クエリ数と時間）を、計測値に小さな余裕を足した値で定め、超えたら失敗する
> テストで守ってください。変更が触れる地図の各消費者を、同じコミットで更新してください。前と
> 後の表、予算、テーブルごとの保持を `docs/PERSISTENCE.md` に記録してください。

何を求めているか：変更ごとに一つのコミット。前と後が帰属可能になるように。同じデータの上の同
じ計器（データが変わるなら、数字は何も言わない）。テスト付きの予算。それがN+1ループが三か月
後に戻ってくるのを防ぐものだ。そして永続化に適用された第11段の対称性。

## 3. 期待される成果物

- リポジトリの中の、テスト付きのクエリの計器。
- `docs/PERSISTENCE.md`、変更ごとの前と後の表、経路ごとの予算、テーブルごとの保持とともに。
- インデックス、ページング、バッチ、保持が適用され、一つにつき一コミット、回帰とエンドツーエ
  ンドが緑で。
- 予算ごとに一つの、超えたら失敗するテスト。

## 4. 完全性の検証

- あなた自身で計器を前と後に走らせること（エージェントが二つのコマンドをくれる）：表と一致し
  ますか？
- 重要なフローの中にテーブル全体を読むクエリがありますか？ なぜ残ったのですか？
- 各テーブルに保持の方針が書かれていますか、たとえ「永久に」でも？
- 予算にテストがありますか？ わざと一つ超えて赤を見せるよう求めてください。
- 最も遅い画面は、量のあるデータで、サイジングが期待した通りの時間ですか？

## 5. 警告サイン

- 計測が骨組みのサンプルデータで行われた。十行では何でも速い。
- エージェントが「別のデータベースへ移行する」か「データ層を書き直す」と提案する。それは第3
  段であり、そこへ戻る必要があるならそれは最適化ではなくあなたの決定だ。
- 数字は良くなったが、あるフローのエンドツーエンドが通らなくなった。インデックスはフローを壊
  さない。保持やページングは壊す：地図の消費者が一人抜けていた。
- 予算がない。予算なしでは、最適化は次のブロックまでしかもたない。
