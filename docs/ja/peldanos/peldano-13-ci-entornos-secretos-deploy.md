# ステップ 13 — プロダクトの一部としての継続的インテグレーション、環境、秘密、デプロイ（段の契約）

**区間：** 運用。
**いつ：** インテグレーションの連鎖とテスト環境へのデプロイは第4段で組む。本番への締め
（実環境、サーバー上の秘密、昇格、試されたロールバック、秘密に対する錠）は、監査と錠の後、
本番リリース区間で行う。各デプロイのルーチンは運用全体で適用する。
**形式：** 組むために一回の送信。各デプロイにはルーチン。
**規模：** ユーザーのいるすべてのプロジェクトで必須。小さいプロジェクトなら「継続的インテグ
レーション」は一つのGitHubアクションで、「環境」は同じサーバー上の二つのフォルダでよい。
譲れないのは、テストが自動で走ること、設定がリポジトリにないこと、ロールバックがあることだ。

## 何のためか

本番に至ることを再現可能なパッケージにすること：テストは**一度**走り、設定はリポジトリの
外に住み、秘密は出回らない。コミットごとに三度走るテストと燃え尽きたクォータ
[Ref. 39](../REFERENCIAS.md#ref-39)、遅く発見されたために保留項目を重ねて強化されたデプロイ
[Ref. 32](../REFERENCIAS.md#ref-32)、チャットに貼られた秘密 [Ref. 42](../REFERENCIAS.md#ref-42)
を防ぐ。

秘密については、例外なく反射として採用すべきルールがある：**チャット、ログ、コミットで見
られた秘密はもう秘密ではない**。「誰も見なかった」「後で消した」は関係ない。ローテーション
する。ローテーションは十分で済む。誰かが使ったか調べるのは不可能だ。

## 1. 必要な文脈

ここに続くのは一般的なリストです。各プロンプトの前にあなたが作り終えていなければならない具体
的なファイルは、その内容と最低限受け入れられる状態とともに、第2節の、それぞれのプロンプトに
先立つ「プロンプトを送る前に」の枠に書いてあります。

- **環境とアクセスの調査**、一般的な形で：どんな環境があるか（テスト、本番）、どこで動く
  か、誰がアクセスを持つか、一方から他方へどう昇格するか、どんな秘密が存在し今日どこに
  住んでいるか、継続的インテグレーションのクォータはどれだけあるか。エージェントが十分か
  評価して質問する。
- 継続的インテグレーションとテストへのデプロイを持つ骨組み（第4段）。

## 2. プロンプト

**最初：**

**プロンプトを送る前に**、次のものが存在していなければなりません。作るのはあなた（または業務
側とあなた）で、エージェントではありません：

- `docs/ENVIRONMENTS_SURVEY.md`（第4段）、本番に向けて足りないものを補ったもの：ドメインと、
  それを管理するのは誰か。秘密がサーバーのどこに住むことになるか（環境ファイル、金庫）、そし
  てどれがあるか（名前だけ。値は決して書かない）。今、テストから本番へどう昇格しているか、何
  かあるなら。誰が本番に触れられるか。継続的インテグレーションの枠がどれだけあるか（提供者の
  プランの上限）と、どれだけ消費したか。今日ならどう巻き戻すか。プロンプトはこれを「the
  environments and access survey」と呼びます。どこにあるかを言ってください。
- エージェントのための本番へのアクセス、あなたが決めたもの：どれを、どの資格情報で。そしてそ
  の資格情報はリポジトリとチャットの外に。
- 継続的インテグレーションとテスト環境へのデプロイが機能している骨組み（第4段）、そしてコマ
  ンドの書かれた `docs/STATUS.md`。
- 最低限受け入れられる状態：秘密がどこに住むことになるかと、枠がどれだけ残っているかを知って
  いること。枠を知らないなら、先に調べてください。この段が存在する理由の一つがそれです。

> We are going to close the path to production. Read the environments and access survey.
> Evaluate whether you have what is needed to deploy to production safely (access, domain,
> where the secrets live, how to roll back); if anything is missing, ask me. Then set up: (1)
> continuous integration runs the full test suite exactly once per commit; (2) the deployment
> waits for that run's result and only packages and uploads, without running tests again; (3)
> each environment's configuration lives on the server (environment file or vault), never in the
> repository; (4) a written procedure to promote from the test environment to production, which
> can be run twice without breaking anything; (5) the rollback, tested; (6) an automatic check
> that prevents committing a secret. Document all of it in `docs/DEPLOYMENT.md` so that a person
> can do it by hand without you. Reply in my language.

> [ja]
> 本番への道を締めます。環境とアクセスの調査を読んでください。本番へ安全にデプロイするのに
> 必要なもの（アクセス、ドメイン、秘密がどこに住むか、どうロールバックするか）があるか評価
> してください。何か欠けていれば、私に求めてください。次に組んでください：(1) 継続的インテ
> グレーションは完全なテスト群をコミットごとに正確に一度実行する。(2) デプロイはその実行の
> 結果を待ち、テストを再実行せずにパッケージしてアップロードするだけ。(3) 各環境の設定は
> サーバー上（環境ファイルまたは金庫）に住み、決してリポジトリにはない。(4) テスト環境から
> 本番へ昇格する書かれた手順、何も壊さず二度実行できるもの。(5) ロールバック、試されたもの。
> (6) 秘密のコミットを防ぐ自動チェック。すべてを `docs/DEPLOYMENT.md` に、人があなたなしで
> 手でできるように文書化してください。私の言語で答えてください。

何を求めているか、条項ごとに：始める前のアクセス。コミットごとに**一度だけ**のテスト（三度
走らせたのがクォータを燃やした）。パッケージするだけのデプロイ。リポジトリ外の設定。繰り
返し可能な手順としての昇格。**試された**ロールバック（一度も試されていないロールバックは
存在しない）。コミットの秘密に対する錠。そして人のための文書化、インフラに適用された第14段
だ。

**各デプロイのルーチン：**

**プロンプトを送る前に**、次のものを手元に用意しておいてください：

- `docs/WORKING_AGREEMENT.md`、ルーチンが入る先。
- `docs/DEPLOYMENT.md`（この段の最初のプロンプト）、書かれていて、あなたが読んだもの：あなた
  一人でそれに従えますか？
- 実際のデプロイのたびに、さらに：正確なバージョンでの完全なエンドツーエンドのテスト群が緑で
  あること（第7段、ブロックの締め）、そして初めてのデプロイなら監査が済んでいること（第11
  段）。
- 最低限受け入れられる状態：利用者が現れる前に、巻き戻しが少なくとも一度試されていること。

> Before touching production: the test environment is green with the same version; the
> rollback is ready; and tell me what changes in the configuration. After deploying: show me
> the version running in production and an end-to-end check on production, read-only.

> [ja]
> 本番に触れる前に：テスト環境が同じバージョンで緑である。ロールバックの準備ができている。
> そして設定で何が変わるかを私に教えてください。デプロイ後：本番で動いているバージョンと、
> 本番に対する読み取り専用のエンドツーエンド検証を見せてください。

何を求めているか：三つの事前条件（同じバージョンでテストが緑、ロールバック準備済み、設定
の変更が告知済み）と二つの事後の証明（動いているバージョンと、何も書かないエンドツーエンド
検証）。

**チャットやコミットに秘密が現れたら：**

**プロンプトを送る前に**、次のものを手元に用意しておいてください：

- 特定された秘密：どれか（その名前。値は決して書かない）、どこに現れたか（チャット、コミッ
  ト、ログ）、いつか。コミットに現れたなら、そのコミット。
- それが生成される場所（提供者の管理画面）へのあなたのアクセス。エージェントが独りで回せない
  場合に備えて。回すのはあなたか、あなたの資格情報を使ったエージェントですが、先送りはしませ
  ん。
- 最低限受け入れられる状態：秘密の名前とどこで見えたかを言えること。そして例外のないルール：
  このプロンプトは「あとで」送るものではありません。

> That secret is compromised: rotate it now, tell me everywhere else it was used, and add the
> check that would have caught it.

> [ja]
> その秘密は漏洩しました：今すぐローテーションし、他にどこで使われていたか私に教え、それを
> 捕まえたはずのチェックを追加してください。

何を求めているか：即時のローテーション、他にどこにあったかの目録、そしてそれを検知した
はずの検証、次回はチャットに届かないように。

## 3. 期待される成果物

- コミットごとに一度だけ走る継続的インテグレーション、実行へのリンク付き。
- インテグレーションを待ちパッケージするだけのデプロイ。計測済み：前後でどれだけかかるか。
- リポジトリ外の設定。リポジトリには値なしの例だけ。
- `docs/DEPLOYMENT.md`：どうデプロイし、昇格し、ロールバックするか、一歩ずつ、人のために。
- 少なくとも一度試されたロールバック、その証拠付き。
- 有効な秘密対策の検証（アップロードの試みが一つ、拒否された）。
- 月ごとに消費された継続的インテグレーションのクォータの記録。

## 4. 完全性の検証

- コミットごとにテスト群は何度走るか？ 一度でなければならない。リンクを求めること。
- リポジトリに実際の設定値（鍵、パスワード、内部URL）があるか？ エージェントに検索させ、
  空の検索結果を見せてもらうこと。
- エージェントなしで、あなた一人で `docs/DEPLOYMENT.md` を追えるか？ その問いを持って読む
  こと。
- ロールバックは試されたか？ いつ？ どんな証拠があるか？
- プロジェクト中にチャットに秘密が貼られたか？ そうなら、ローテーションされたか？
- 今月の継続的インテグレーションのクォータがどれだけ残っているか知っているか？

## 5. 警告サイン

- 本番へのデプロイが「手で、素早く、小さな変更だから」行われる。小さな変更こそ本番を壊す。
  誰もテストしないからだ。
- 設定の例ファイルに本物に見える値がある。おそらく本物だ。
- ロールバックを最後に試したのがいつか誰も言えない。
